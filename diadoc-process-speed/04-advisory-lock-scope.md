# Task 04 (P2): Advisory-lock на ремонт удерживается всю транзакцию записи

## Проблема

`AbstractDrRepairPacketParserService.java:327`:

```java
advisoryLock.acquireTxLock(lockPrefix() + finalRepairUid);
```

Лок — транзакционный (`ProcessingAdvisoryLock.java:21-24`, `pg_advisory_xact_lock`),
ключ — **ремонт** (`"tr2:" + repairUid` / `"plan:" + repairUid`), а не пакет. Берётся
внутри `transactionTemplate.execute` (`:315-343`), который оборачивает весь конвейер
записи `fillEntitiesAndSave` (`:346-410`):

- `recreateContract` — delete+insert контракта и всех дочерних строк (task 06);
- `saveRdvRows` / `saveMh1Rows` / `saveMh3Rows` / `mergeMh1mPackets`;
- `mhDetailOriginService.resolveOrigins` — со всем N+1 (task 02);
- `validatePacket`, `validateByRepairUid` — с повторной загрузкой всех строк ремонта
  (`packetRowsLoader.loadRdvRows/loadMhRows/loadEquipmentRows`).

## Почему тормозит

Пока один пакет ремонта обрабатывается, **все** конкурентные пакеты и повторы по тому же
ремонту ждут на `pg_advisory_xact_lock`, удерживая HTTP-поток и соединение БД. NiFi,
присылающий пакет за пакетом по одному ремонту, работает строго последовательно, и к
времени обработки прибавляется время ожидания. При N+1 (task 02) и seq-scan'ах
(tasks 01, 03) одна итерация конвейера сама по себе долгая — лок многократно усиливает
это.

Заметим: лок на ремонте, а не на пакете — осознанное требование (delete+insert строк
контракта не должны чередоваться между транзакциями, комментарий `:325-326`). Сужать
нужно не ключ, а **время удержания**.

## Фикс

Разбить одну «длинную» транзакцию на две, оставив под локом только критическую секцию:

1. **Транзакция 1 (под advisory-локом):** очистка + пересоздание контракта + строки
   РДВ/МХ/комплектации + архив — всё, что должно быть атомарно и не чередоваться.
2. **Транзакция 2 (после commit, лок уже снят):** `resolveOrigins`, `validatePacket`,
   `validateByRepairUid`, дописывание отметок на архив/контракт.

Обе фазы идемпотентны при переобработке (полный recreate при следующем пакете), поэтому
окно между ними — лишь чуть более длительный период «строки есть, происхождение ещё не
проставлено», что уже сегодня наблюдается при разрыве соединения.

Альтернатива (меньше эффект): оставить одну транзакцию, но вынести `resolveOrigins`
и валидации в `afterCommit`-фазу той же транзакции отдельной транзакцией.

Порядок: выполнять **после task 02** — когда тело транзакции станет дешёвым, эффект от
её разделения меньше, но сериализация NiFi-потока всё равно уходит.
