# Автоподписание: решение по статусу проверки и вкладка в окне результата

## Что появилось

- **Автосогласование (`/api/diadoc/approve`) проверяет четыре вещи:**
  1. включена ли настройка для типа пакета;
  2. итог строки `packet_check` — «Норма». Нарушение и **предупреждение** теперь запрещают
     одинаково (раньше запрещало только нарушение);
  3. в пакете нет подписанных или отклонённых документов;
  4. пакет ещё не во флоу подписания.
- **Повторное согласование ничего не делает, и видно почему:**
  - причина «Пакет уже автосогласован <дата>, статус подписания: …», если в
    `diadoc_packet_flow.approved_by` записано «Автомат». Именно эту строку пишет `/approve`, а
    не «system»;
  - «Пакет отправлен на согласование вручную: <пользователь>, <дата>, статус…», если согласовал
    человек.
- **Причина «не норма» короткая:** «Результат проверки пакета: Нарушение / Предупреждение», без
  текстов позиций.
- **Окно «Результат проверки» на карточке пакета — две вкладки:**
  - «Проверки (N)» — позиции, как раньше;
  - «Автоподписание» — только показывает решение, ничего не согласует:

| Состояние | Что видно |
|---|---|
| Не настроено / Отключено | серый заголовок и строка-пояснение, без таблицы |
| Автосогласован | зелёный заголовок, дата и статус подписания |
| Отправлен на согласование вручную | заголовок, кто, когда, статус |
| Можно / Нельзя | заголовок и таблица «Проверка — Результат — Подробности» |

  Строки таблицы: «Настройка автосогласования», «Результат проверки пакета» (Норма / Нарушение /
  Предупреждение — «Позиции — на вкладке «Проверки»»), «Подписанные или отклонённые документы»
  (Нет / Есть + документы), «Согласование пакета». Результат — зелёный или красный.

- Карточка пакета → кнопка результата проверки (Норма / Нарушение / …) → вкладка
  «Автоподписание». У СЧФ вкладки нет: она не автоподписывается.
- **Демо-данные в локальной БД** (`docker-rvk-db-1`, загружены `demo-data.sql`), карточка
  `/diadoc-packet/<messageId>`:

| messageId | Вариант |
|---|---|
| `a5170000-0000-0000-0000-000000000001` | ВУ-23, нельзя: нарушение (наработан `processPacket`, «Контрагент ЦДИ не найден») |
| `a5170000-0000-0000-0000-000000000002` | ВУ-23, нельзя: предупреждение |
| `a5170000-0000-0000-0000-000000000003` | ВУ-23, нельзя: документ подписан и документ отклонён в Диадоке |
| `a5170000-0000-0000-0000-000000000004` | ВУ-23, можно |
| `a5170000-0000-0000-0000-000000000005` | ВУ-23, автосогласован |

## Как устроено

- `AutoSignDecisionService.evaluate`:
  - `checkStatusBlocker` — итог пересчитанных позиций (`PacketCheckItem.summaryStatus`, так же
    считается `packet_check.status`) ≠ NORM → `CHECK_NOT_NORM`;
  - `approvedBlocker` — при недоступном согласовании (`checkCanApprove`) читает `PacketFlow` и даёт
    `ALREADY_AUTO_APPROVED` или `SENT_MANUALLY`.
- Коды в `AutoSignBlockerCode`: `CHECK_VIOLATION` → `CHECK_NOT_NORM`; `PACKET_APPROVAL_UNAVAILABLE`
  → `ALREADY_AUTO_APPROVED` / `SENT_MANUALLY`.
- `PacketApprovalService.AUTO_APPROVER` = «Автомат» — общая константа, её же берёт
  `PacketSigningService`.
- `AutoSignView` (новый record) — модель вкладки. Её строит `PacketCheckDisplayService.autoSignView`
  из кодов причин; `PacketCheckDetails` получил поле `autoSignView`.
- `DiadocPacketDetailView.openCheckResultDialog` — `TabSheet` с двумя вкладками,
  `autoSignContent` и `autoSignStepsGrid`. Прежний `autoSignBlock` удалён.
- Тексты — `messages_ru.properties`: `autoSign.checkNotNorm`, `alreadyAutoApproved`, `sentManually`,
  `autoSignTab.*`, `checkResult.tab*` / `checkResult.autoSign.*`. Ключи `checkViolation`,
  `packetApprovalUnavailable`, `checkResult.autoSignAllowed/Blocked` удалены.

## Решено без вас

- Не настроено, отключено, автосогласован, отправлен вручную — одной строкой без таблицы: для них
  остальные проверки ничего не решают. «Автосогласован» важнее настройки: пакет мог быть
  согласован до её выключения.
- Возвращённый на доработку пакет (`SENT_FOR_REVISION`) по-прежнему можно автосогласовать снова,
  как было в `checkCanApprove`.
- Вкладка строится из кодов причин того же решения, что у `/approve`, — второй логики для экрана нет.
- Неизвестный код причины на вкладке попадает в строку «Прочее», а не теряется.
- Вход в браузере — `admin` / `admin`: у локального `user` в `sso_user` нет пароля, поэтому
  `user` / `user` из `CLAUDE.md` локально не работает.
