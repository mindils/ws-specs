# T05 — Карточка претензии: шапка, вкладки, зоны ДЭПС/ДЮ, сроки

Статус: todo
План: [plan.md](../../plan.md)
Зависимости: [T03](../T03/task.md)
Сложность: hard — две сущности в одном `DataContext`, пять вкладок-фрагментов
(~110 полей), read-only по ролям, предварительный расчёт сроков без
сохранения; много мест для ошибок в XML
Сложность проверки: hard — браузер под двумя ролями, сохранение обеих зон,
проверка read-only чужой зоны, вкладка «Сроки» до и после сохранения
Актуальная проверка: нет

## Коротко

Единственная карточка претензии повторяет старую форму «Редактирование
претензий»: read-only шапка отцепки и вкладки «Документы», «Допретензионная
работа», «Претензия», «Судебная работа», плюс новая read-only вкладка
«Сроки». ДЭПС редактирует первые две вкладки, ДЮ — вторые две; чужая зона
видна, но заблокирована правами. Сохранение одной кнопкой пишет обе таблицы
и запускает пересчёт сроков.

## Результат и контекст

Карточки нет. Редактируемая сущность — `LegalTechClaimDeps`; парная
`LegalTechClaimDu` (1:1 по `deps_id`, создаётся вместе с претензией
сервисом T03 или загрузкой); шапка — `deps.repair` (`LegalTechClaim`).
Раскладка полей по вкладкам, перечень полей и предупреждение о двух похожих
парах — раздел «Общие решения» плана (контракт, менять нельзя); первоисточник
— скриншоты `specs/dr-warranty-repair/*.png` и их текстовое описание в
разделе «Материалы» плана. Роли и `@ViewPolicy` на `legal_TechClaim.detail`
заведены в T03.

## Реализация

Скилы: `jmix-create-detail-view`, `jmix-create-fragment`,
`jmix-add-i18n-keys`, `jmix-style-ui`, `jmix-verify-api-symbol`,
`jmix-configure-fetch-plan`.

- `StandardDetailView<LegalTechClaimDeps>`,
  `@ViewController("legal_TechClaim.detail")`,
  `@Route("legal-tech-claims/:id")`, `@EditedEntityContainer("depsDc")`.
  Fetch plan `deps` с `repair` (все поля шапки) — без N+1 и unfetched.
- `du`: `instanceContainer id="duDc" class="…LegalTechClaimDu"` +
  `instanceLoader` с запросом
  `select d from legal_TechClaimDu d where d.deps.id = :depsId` в том же
  `DataContext`; параметр — из `deps.id` в `onBeforeShow`/`onReady`. Если
  строки нет — создать `du` через `dataContext.create`, установить `deps`,
  положить в `duDc` (для ДЭПС создание тоже штатно: сервис T03 всегда
  создаёт пару, но загруженные данные могут прийти без `du`; создавать в
  контексте под пользователем можно только при праве CREATE, иначе оставить
  контейнер пустым и показать сообщение на вкладках ДЮ). Одна кнопка
  «Сохранить» (`saveClose`/`save`) пишет изменённые сущности контекста.
- Шапка — `formLayout` над `deps.repair.*` read-only; блок виновника —
  поля `deps.warranty*` (редактируемые ДЭПС): переключатель `warrantyIsVrp`
  скрывает/показывает пары полей ВРП (`warrantyDepoCode`, `warrantyType`)
  и текстового контрагента (`warrantyName`); `warrantyNote`,
  `warrantyRailwayCode` рядом.
- `tabSheet` из пяти вкладок; каждая — фрагмент со своим XML, получающий
  `depsDc`/`duDc` через provided-контейнеры (образец `tabSheet` —
  `pt/view/ptrepaircontract/pt-repair-contract-detail-view.xml`, фрагменты —
  `pt/view/ptrepairclaim/pt-repair-claim-detail-view.xml`). Группировка и
  подписи блоков — как на скриншотах; enum-поля — `comboBox`/`select` по
  enum-аксессорам; булевы «подлежит/не подлежит» — `select` с двумя
  подписями через `msg://`, не чекбокс.
- Вычисляемые суммы на вкладке «Документы» (штраф = `downtimeDays ×
  downtimePenaltyPerDay`, «Итого провозные платежи», «ВСЕГО к возмещению») —
  read-only поля, пересчитываемые в контроллере по тем же формулам, что во
  view (`result.md` T02 прежней работы); бизнес-логику не дублировать в
  сущность — допустимо вынести общий калькулятор в `service`, если формула
  нужна и view, и форме (тогда тест на совпадение).
- Read-only по зонам: полагаться на штатное поведение Jmix — компонент,
  привязанный к атрибуту без права MODIFY, становится read-only. Проверить в
  IT/браузере; если для отдельного компонента не срабатывает — явно
  `setReadOnly(true)` по проверке `AccessManager` с
  `EntityAttributeContext`, без списка полей в контроллере (проходить по
  компонентам вкладки). Вкладки чужой зоны не скрывать.
- Вкладка «Сроки»: `dataGrid` над DTO (семь строк: этап, срок, дата факта,
  степень с CSS-классом как в T04). Данные — `TechClaimDeadlineService`:
  собрать `ClaimTermSource` из текущих значений `depsDc`/`duDc` (поля
  перечислены в javadoc `ClaimTermSource`), `calculator.calculate(source,
  context.calendar(), context.norms())` с `loadReferenceContext()` и
  `describe(source, calculation, dateProvider.currentDate())`; пересчёт по
  изменению любого исходного поля (подписка на `ItemPropertyChangeEvent`
  обоих контейнеров) и при открытии. Ошибку календаря/нормы
  (`WorkCalendarGapException`, `ClaimTermNormNotFoundException`) показывать
  текстом на вкладке, а не падать. Ниже — строка «Сохранённый расчёт от
  <calculatedDate>, ревизия N» или «Требуется пересчёт».
- Сохранение: штатный `save`; слушатели T08 пересчитывают сроки в той же
  транзакции; ошибка расчёта откатывает сохранение — показать её
  пользователю (`Notification` из сообщения исключения), форму не закрывать.
- Отмена не меняет БД. `@ViewPolicy` уже есть (T03). Иконки — только
  существующие `VaadinIcon` или без иконок.

## Критерии приёмки

- C1: карточка открывается по `deps.id`; шапка заполнена и недоступна для
  редактирования; блок виновника редактируем под ДЭПС.
- C2: под ДЭПС редактируются все поля «Документов» и «Допретензионной
  работы», вкладки «Претензия» и «Судебная работа» полностью read-only;
  сохранение записывает `deps`, `du` не меняется.
- C3: под ДЮ — наоборот; сохранение записывает `du`, `deps` не меняется.
- C4: под админом редактируются обе зоны; одна кнопка сохраняет обе таблицы.
- C5: вычисляемые суммы на форме совпадают с колонками view для той же
  претензии после сохранения.
- C6: вкладка «Сроки» до сохранения меняется при правке исходной даты
  (например, `docPackageReadyDate`), после сохранения совпадает со
  строкой view/таблицы расчёта; отмена возвращает БД в прежнее состояние;
  ошибка календаря (дата в 2027 году) показана текстом, сохранение отклонено
  с понятным сообщением, данные не записаны.
- C7: все 110+ полей контракта присутствуют на своих вкладках (сверка по
  списку из плана), сырых `msg://` нет, error overlay и серверных исключений
  нет; `./gradlew :app:test` — `0 failing`.

## Самопроверка исполнителя

Gate 1: инспекция IDE по каждому XML/Java; без IDE — `compileJava`,
`jmix-ide-static-analysis`, скрипт сверки `msg://` с бандлом и property
path с полями entity. Gate 2 частично: один IT раздела (контекст
поднимается с новыми view). Smoke браузером под админом: открыть карточку
из URL `legal-tech-claims/<id>`, пройти пять вкладок, изменить одно поле
ДЭПС и одно ДЮ, сохранить, перечитать из БД. Полный `:app:test` и проход
под ролями — проверяющему.

## Независимая проверка

Последовательно после T03. `./gradlew :app:test` целиком. `bootRun` +
`playwright-cli`/агент `qa`: три пользователя (ДЭПС, ДЮ, админ); фикстура —
претензия с `du`, претензия без `du`, претензия с датой комплекта, дающей
срок в 2027 году. Пройти C1–C7 с проверкой read-only через DOM (`readonly`
атрибут/`aria-readonly`) для каждой вкладки, сохранение и перечитывание
из БД SQL-ом, вкладку «Сроки» до/после сохранения, негативный сценарий
ошибки календаря. Данные убрать. Без браузера —
`render not browser-verified`, таск не `done`.
