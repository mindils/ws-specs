# T04 — Список претензий: колонки отчёта, фильтры, подсветка сроков

Статус: todo
План: [plan.md](../../plan.md)
Зависимости: [T02](../T02/task.md), [T03](../T03/task.md)
Сложность: hard — большой list view (~130 колонок, ~30 фильтров, подсветка
ячеек, кнопка с сервисом), стили темы, меню; образцы есть, но объём и число
мест отказа велики
Сложность проверки: hard — живое приложение и браузер под двумя ролями,
проверка фильтров/сортировки/count на выборке больше страницы, вычисленный CSS
Актуальная проверка: нет

## Коротко

Пользователи ДЭПС и ДЮ работают со списком претензий: ищут по параметрам
старой процедуры, видят сроки этапов с подсветкой просрочки и открывают
карточку. Таск создаёт единственный list view раздела над view
`VLegalTechClaim` со всеми колонками отчёта «Перечень вагонов» (видимый
минимум по умолчанию), фильтрами, подсветкой семи сроков, кнопкой «Создать
претензию» и пунктом меню.

## Результат и контекст

Экранов у раздела нет. Источник данных — `VLegalTechClaim` после T02 (все
колонки со статусом ≠ `нет` в [report-columns.md](../../input/report-columns.md),
семь `*DueDate`, семь `*OverdueLevel`, `deadlinesOutdated`). Роли и политики
на view id `legal_TechClaim.list`/`legal_TechClaim.detail` и menu id
`legal_TechClaim.list` уже заведены в T03 — использовать ровно эти id.
Карточка `legal_TechClaim.detail` делается в T05 параллельно: открытие из
списка настраивать на этот id; до готовности T05 переход даёт
`NoSuchViewException` — это ожидаемо и в проверке T04 не считается отказом,
если T05 ещё не `done`.

## Реализация

Скилы: `jmix-create-list-view`, `jmix-create-fragment`, `jmix-style-ui`,
`jmix-add-i18n-keys`, `jmix-verify-api-symbol`, `jmix-add-dialog-detail-flow`.

- `StandardListView<VLegalTechClaim>`, `@ViewController("legal_TechClaim.list")`,
  `@Route("legal-tech-claims")`, `@ViewDescriptor`. Загрузка страницами
  (`pagination`), без загрузки всего набора; сортировка по умолчанию —
  `defectDate desc`.
- Колонки: все из `report-columns.md` со статусом ≠ `нет`, в порядке и с
  заголовками отчёта (путь «блок / поле» сокращать до читаемого заголовка,
  блок — в `header`/tooltip). По умолчанию видны колонки с `да`; остальные
  скрыты (`visible="false"`) и включаются `gridColumnVisibility` — образец
  `rp/view/vrpoperwaglist/v-rp-oper-wag-list-view.xml`. Enum-поля — через
  enum-аксессоры entity.
- Семь колонок сроков: рендерер выводит дату; ячейке добавляется класс
  `legal-tech-claim-overdue-<level>` по соответствующему `*OverdueLevel`, а
  в title/tooltip — текст степени из `msg://` («Просрочка 1–10 раб. дн.» и
  т. п.). Подсвечивается только ячейка. Отдельная колонка-признак
  «Требуется пересчёт» по `deadlinesOutdated`, видимая по умолчанию.
- CSS: три класса в теме `app` с фиксированной палитрой (жёлтый, оранжевый,
  красный) с использованием токенов активной темы там, где они существуют;
  перед использованием custom property убедиться, что он определён в теме
  (скил `jmix-style-ui`). Образец подключения — `themes/app/view/dt/…css`.
- Фильтры (только `propertyFilter`/`jpqlFilter`; образец с фрагментом —
  `pt/view/ptrepairclaim/pt-repair-claim-list-view.xml`): период ремонта
  (`repairDate`), период браковки (`defectDate`), номер вагона, дорога
  (`railwayCode`/`railwayMnkd`), депо (`depoCode`/`depoName`), виновник
  (`warrantyType`, `warrantyName`, `warrantyDepoCode`), вид ремонта,
  подлежит/не подлежит, результат претензии, маска номера претензии
  (`claimNumber like`), реестр ДЮ (`lawRegistryNum`, период
  `lawRegistryDate`), ПСР (`psrNumber`, период `claimTransferDateEffective`),
  подразделение допретензионной работы, гарантийные КП (`guaranteeKpCount`),
  суммы (`totalReimbursement`, `claimCost`, `underpaidCost`), по каждому из
  семи сроков — диапазон `*DueDate` и выбор степени `*OverdueLevel`
  (нет / 1 / 2 / 3), признак «Требуется пересчёт». Фильтры применяются к
  loader-у (условия уходят в SQL), не к загруженной странице.
- Кнопка «Создать претензию»: доступна при выделенной строке; вызывает
  `TechClaimService.createClaim(selected.repairUid)` и открывает
  `legal_TechClaim.detail` для созданной `deps` (диалогом или навигацией —
  выбрать одно и применить и для «Изменить»); после закрытия карточки —
  перезагрузить список. Кнопка видна только при праве CREATE на
  `LegalTechClaimDeps` (для ДЮ скрыта/недоступна).
- «Изменить»/двойной клик открывает `legal_TechClaim.detail` с `deps` по
  `id` строки view (`id` view = `deps.id`); действию явно указать
  `viewId` (в T07 прежней работы без этого падало `NoSuchViewException`).
- Меню: `<item view="legal_TechClaim.list" …/>` в узле `legal` с `msg://`
  заголовком «Претензии по технологическим неисправностям».
- Экспорт в Excel — если в проекте есть штатное действие грида
  (`excelExport`), добавить; отдельно не разрабатывать.

## Критерии приёмки

- C1: пункт меню виден пользователям с ролями ДЭПС, ДЮ и админ; список
  открывается, грид наполняется страницами.
- C2: по умолчанию видны только колонки с `да`; через настройку колонок
  включается любая остальная; сырых `msg://` нет.
- C3: каждый фильтр меняет выборку и count (проверить хотя бы: период
  браковки, номер вагона, подлежит/не подлежит, номер претензии, степень
  просрочки одного срока, диапазон одного срока, «Требуется пересчёт», сумма)
  на выборке больше одной страницы; сортировка по сроку и по сумме — в БД.
- C4: ячейки семи сроков имеют вычисленный в браузере фон, соответствующий
  степени; соседние ячейки одной строки с другими степенями независимы;
  tooltip содержит текст степени.
- C5: кнопка «Создать претензию» под ДЭПС создаёт претензию `claim_index+1`
  и открывает карточку; под ДЮ кнопка недоступна.
- C6: открытие строки ведёт в `legal_TechClaim.detail` (при `done` T05).
- C7: нет error overlay и серверных исключений в логе на всех действиях;
  `./gradlew :app:test` — `0 failing`.

## Самопроверка исполнителя

Gate 1: инспекция IDE по каждому созданному файлу; без IDE —
`./gradlew :app:compileJava` + механические проверки
`jmix-ide-static-analysis` + сверка всех `msg://` XML с бандлом скриптом.
Gate 2 частично: `./gradlew :app:test --tests "ru.fgk.ws.app.it.TechClaimViewIT"`
(контекст с новым view поднимается; красный контекст = отравленный реестр
view — чинить сразу). Один smoke браузером: открыть список под `user`
(назначить роль админа), убедиться, что грид наполнен и одна ячейка срока
подсвечена. `bootRun` в фоне, дождаться `/actuator/health` = UP, погасить.
Полный `:app:test` и полный render-проход — проверяющему.

## Независимая проверка

Последовательно после T05. `./gradlew :app:test` целиком. Затем `bootRun`,
`playwright-cli` (или агент `qa` в Herdr): подготовить фикстуры — не менее
60 претензий (больше страницы) с разными степенями просрочки, устаревшим и
отсутствующим расчётом (SQL или IT-хелпер; убрать после проверки). Пройти
C1–C7 под пользователем с ролью ДЭПС, затем ДЮ, затем админ: скриншоты
грида с подсветкой, вычисленный `background-color` трёх ячеек через
`getComputedStyle`, count до/после фильтра, консоль браузера и лог
приложения без ошибок. Без браузера — `render not browser-verified`,
таск не `done`.
