## Коротко

Делаем страницу «Освидетельствования контейнеров» и вкладку
«Освидетельствования» в карточке: одна запись, одна форма. Пользователь вручную
задаёт вид, три календарные даты, исполнителя и файл акта; следующая дата в
реестре при этом не меняется.

## Реализация

- Skills: `jmix-create-list-view`, `jmix-create-detail-view`,
  `jmix-create-fragment`, `jmix-add-dialog-detail-flow`,
  `jmix-configure-fetch-plan`, `jmix-add-i18n-keys`, `jmix-create-resource-role`,
  `jmix-create-test`.
- Список: фильтры по контейнеру, виду, датам; экспорт; создать/редактировать/
  копировать/удалить.
- Detail: контейнер — `entityComboBox` по номеру + `entity_lookup` на реестр,
  обязателен в UI; из вкладки контейнер предустановлен и read-only. Даты —
  `datePicker` (`LocalDate`). Исполнитель — `entityComboBox` по `VOrgPassport`.
  Файл акта — `fileStorageUploadField`, просмотр/скачивание как в T03.
- Вкладка — фрагмент по контракту T03: грид с пагинацией, диалог той же
  detail-формы, перезагрузка после SAVE.
- Никакой логики обновления `next_survey_date` контейнера.

## Критерии приёмки

- C1: Запись, созданная из списка, видна во вкладке правильного контейнера и
  наоборот; дублей нет.
- C2: Lookup находит контейнер по части номера; даты после сохранения и
  повторного открытия календарные, без времени.
- C3: Создание/изменение/удаление/перенос на другой контейнер не меняет
  `next_survey_date` ни у одного контейнера (интеграционный тест на двух
  контейнерах).
- C4: Файл акта загружается, просматривается, заменяется; копия записи без
  файла и истории; cancel ничего не сохраняет; удаление — soft delete.
- C5: Роль read не пишет; роль edit имеет все view/attribute-политики в обеих
  точках входа; экспорт согласован со списком.
