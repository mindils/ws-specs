## Результат и контекст

Получить persistence-основу всего контейнерного раздела: новые сущности, таблицы, связи, полный аудит версий и инварианты сохранения/удаления. Экраны поставляются последующими тасками. Текущая БД содержит НСИ организаций/станций и Jmix audit, но наличие audit-аддона само по себе не доказывает требуемую историю полных версий.

Уточнение пользователя 2026-09-12: контейнерного раздела в текущей РВК раньше не было. Обязательно создать самостоятельную таблицу конкретных контейнеров `cnt_container` по приложенному старому `"MDM_DATA".cont`. Таблицы типов и моделей не заменяют её. Она изначально пуста и наполняется ручным созданием через форму T03, без внешней синхронизации или неявного создания по записи ремонта.

Вход: [общие контракты и матрица](../../contracts.md), [исходный DDL](../../input/issue.md). Сначала проверить актуальное состояние кода: в рабочей копии есть изменения других задач, их не включать в эту работу и не откатывать.

## Реализация

- Применить `jmix-create-entity`, `jmix-create-liquibase-changelog`, `jmix-create-service`, `jmix-add-entity-event-listener`, `jmix-configure-fetch-plan`, `jmix-create-enum` при введении enum действий истории, `jmix-add-i18n-keys`, `jmix-create-test` и skills проверок.
- Сопоставить всю матрицу с сущностями/колонками `container`/`cnt_*`, включая новые ручные операции и накладные, договоры, гарантии, ремонты, акты и таблицы связи общих документов. Зафиксировать фактические имена, типы, длины, индексы и Java/entity-id в contracts.md; не менять согласованные бизнес-поля. Проверить существующие типы PK `VOrgPassport` и `VStation` до объявления ссылок.
- Основной каталог миграций: `app/src/main/resources/ru/fgk/ws/app/liquibase/changelog/01-tbl/`. Новые changelog подхватываются корневым includeAll. Использовать preConditions, `QUOTE_ONLY_RESERVED_WORDS`, author `app`; без FK. Все созданные файлы проверить на существование и непустоту. `migration/ws_store` не изменять.
- До создания справочников записать соответствия общему НСИ: организации/станции/дороги уже существуют и используются также вагонным разделом. Для остальных проверить назначение, поля и ключи; совпадающий общий справочник переиспользовать с фиксацией в contracts.md, несвязанные вагонные справочники не подменяют контейнерные.
- Реализовать нормализацию и глобальную уникальность номера, включая soft-deleted; смена номера сохраняет связи. Разместить инварианты вне UI. Проверить гонку двух сохранений одинакового номера.
- Реализовать soft delete, запреты удаления действующих ссылок и транзакционно согласованное изменение общих документов. Акт/накладная имеет один набор связей без дублей; изменение набора также меняет версию документа.
- Полная история охватывает все новые изменяемые записи и НСИ; механизмы persistence не должны позволять обход через обычный DataManager. Снимки общих документов содержат итоговый набор контейнеров. CREATE/UPDATE/DELETE и снимок атомарны; история не порождает рекурсивную историю.
- Использовать существующие FileRef/хранилище для бизнес-вложений. Не создавать копию MDM data_file. Обеспечить контракт сохранения исторических ссылок без физического удаления прежних файлов.
- Для прав T02 подготовить перечень сущностей/атрибутов и обязательных lookup. Политики пользователей не подменять системным доступом в бизнес-сервисах. Служебная запись истории не должна требовать дать редактору произвольное изменение снимков.

## Критерии приёмки

- C1: Все объекты и поля contracts.md сопоставлены; новая модель не содержит старых технических периодов/lastrec/trans_id и не зависит от старых MDM/ЭТРАН.
- C2: Создание через DataManager получает id/версию/аудит; ссылки имеют корректные типы, nullable и индексы. Миграции согласованы с entities и проходят повторное применение.
- C3: Trim/uppercase работают вне UI; дубль номера, в том числе удалённого, отклоняется; конкурентные сохранения не создают дубликатов.
- C4: Удаление при действующих связях запрещено; после удаления собственных записей/снятия общих связей разрешено. История и удалённые дети не блокируют его навсегда.
- C5: CREATE, UPDATE, soft DELETE дают полные читаемые версии с автором/временем; rollback, отмена/отсутствие изменения не дают ложной версии. Изменение НСИ не переписывает старую подпись.
- C6: Изменение списка контейнеров акта/накладной журналируется атомарно; снятие одной связи не удаляет общий документ. Конфликт конкурентного редактирования обнаруживается.
- C7: Нет автоматических расчётов/дат и изменения следующей даты контейнера из освидетельствования. Согласованные необязательные бизнес-поля не сделаны обязательными без основания.
- C8: На пустых контейнерных таблицах создаётся конкретный контейнер, затем его ремонт и освидетельствование по внутреннему id. Достаточно текущих общих НСИ; внешних данных о контейнере не требуется. Тип/модель остаются отдельными сущностями классификации.

## Проверка

Выполнить [общие гейты](../../plan.md#проверка-и-передача). Для T01 браузер не нужен: UI не создаётся. Gate 1 включает XML миграций и messages, а не только Java.

Интеграционные тесты: create/update/delete каждого семейства сущностей; полные версии и rollback; прямое сохранение вне UI; смена номера; глобальная уникальность; независимость дат; ссылки на удалённые сущности; изменение только состава общих документов; конкурентные create/remove/update. Проверку удаления при связях выполнять для каждого типа связи. Файловую интеграцию через реальное хранилище и UI завершают T03/T07; здесь проверить сохранность FileRef в снимке.

Команды из корня: `./gradlew :app:compileJava`, новые целевые тесты (фактические классы записать в result.md), затем `./gradlew :app:test`. Проверить инфраструктуру до тестов. Не использовать bootRun как гейт.
