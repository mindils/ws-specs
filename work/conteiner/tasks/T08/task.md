## Результат и контекст

Доказать совместную работу всего раздела на актуальном состоянии кода. Найденные интеграционные дефекты исправить в рамках соответствующего кода; затронутые доказательства прошлых тасков перепроверить по протоколу. Зелёные отчёты T01–T07 по отдельности не заменяют этот таск.

## Реализация

- Проверить done у всех зависимостей и транзитивных предшественников, актуальность commit/изменённых файлов и отсутствие открытых fixes. Не начинать с предположения, что старый PASS соответствует текущей рабочей копии.
- Применить skills `jmix-create-test`, `jmix-ide-static-analysis`, `jmix-verify-bootrun`; для найденных production-дефектов — соответствующие skills артефактов. QA исходники не правит: исправляет основной исполнитель и снова передаёт конкретный сценарий на проверку.
- Сверить каждую строку матрицы с моделью, формой и правами. В result.md дать ссылки на реализацию и доказательства покрытия; не оставлять поля «потом», неработающие вкладки, заглушки или сырые SQL-имена вместо подписи.
- Проверить две основные страницы, все девять вкладок и связанные формы НСИ/договоров/гарантий. Меню не содержит ссылок на отсутствующие view. История/файлы доступны из всех новых деталей по контракту.
- Проверить серверную фильтрацию/пагинацию: выборки ограничены контейнером, не загружают целиком общие таблицы и все дочерние коллекции карточки. На тестовых данных двух контейнеров проверить отсутствие утечки чужих строк и дублей от связей. Старые объёмы из issue.md не использовать как обязательную загрузку данных.
- При необходимости добавить один сквозной integration/UI-сценарий, который проверяет взаимодействие подсистем, не дублируя все unit-тесты T01–T07. Записать точные команды запуска и результат по каждому сценарию/роли.

## Критерии приёмки

- C1: Матрица полностью покрыта: две страницы, девять рабочих вкладок, новые НСИ, договоры/гарантии, все согласованные бизнес-поля и вложения.
- C2: Единый сценарий A/B из раздела ниже проходит; общие документы и отдельный список освидетельствований согласованы с карточками.
- C3: Ни один ручной ввод не запускает исключённые интеграции/импорт/расчёты и не требует старой БД. Системные даты старой модели отсутствуют, бизнес-даты сохранены.
- C4: История, soft delete, копирование, уникальность, запреты удаления, отмена и конкурентные изменения работают сквозным образом; старые файлы доступны с корректными правами.
- C5: Три роли проверены и в UI, и в обход UI на сервисном/persistence пути. Недостаточные права не обходятся через lookup, прямой маршрут, историю или скачивание.
- C6: Статическая проверка дана по каждому созданному/изменённому файлу; `./gradlew :app:test` проходит в корректном окружении. Нет необъяснённых пропусков обязательных проверок.
- C7: Браузерный проход подтверждён по всем view/вкладкам/действиям; нет error overlay, серверных исключений, сырых msg://, сломанных кнопок и недоступных по ошибке полей редактора.

## Проверка

Сначала [проверка инфраструктуры и общие гейты](../../plan.md#проверка-и-передача), затем браузер. Команды из корня: `./gradlew :app:compileJava`, целевые сквозные тесты, `./gradlew :app:test`. Проверить принятые проектом форматные проверки для изменённых файлов, не переформатировать чужие изменения. Полный Gate 2 не заменять одним успешным тестом. При ошибке инфраструктуры исправить окружение и повторить точную команду до классификации результата.

Сквозной сценарий:

1. Под НСИ-ролью вручную создать необходимые новые виды/модель/размер/характеристики. Выбрать существующие организацию/станции, не создавать их копий.
2. Начать с пустого реестра контейнеров (изолированные тестовые данные, без очистки пользовательских записей): под редактором через «Создать контейнер» вручную создать A и B; заполнить все бизнес-поля A, разные ручные следующие даты; проверить вычисляемые подписи НСИ и количества модели. Проверить, что это конкретные контейнеры, а не только типы/модели, и что их создание не требует внешнего источника или SQL. Выбирать их вручную во всех последующих формах.
3. Создать характеристику и файл A; добавить освидетельствование из отдельной страницы, открыть из A, изменить даты/акт и убедиться, что следующая дата A не меняется.
4. Добавить ручную операцию A и накладную A+B. Создать договор/гарантии, ремонт A с документом и общий акт A+B. Проверить все девять вкладок A и только относящиеся строки B.
5. Переименовать A, проверить все связи; скопировать A с новым номером и без детей/файлов. Проверить дубль нормализованного номера и конкурентное редактирование.
6. Заменить все виды вложений, открыть прежние снимки и скачать прежние файлы; изменить НСИ и убедиться в неизменности исторических подписей. Отменить формы и проверить отсутствие новых версий/связей.
7. Снять A с накладной/акта, убедиться, что B сохранил документы; вернуть связи через выбор существующих документов. Проверить запрет удаления A и используемых НСИ/договора/гарантии.
8. Удалить/отвязать собственные действующие данные A по явным действиям, затем soft-delete A. История сохраняется, A не появляется в действующих списках; повторное создание с его номером запрещено.
9. Под читателем повторить просмотр, поиск, фильтры, настройки колонок, экспорт и скачивание; попытки изменения/прямого открытия режима edit не разрешены. НСИ-роль без роли ввода не редактирует основные данные.
10. Проверить сообщения, console/server errors, доступность всех кнопок/полей и повторное открытие приложения. Тестовые данные убрать, не затрагивая пользовательские записи и процессы.

В Herdr браузер проверяет `qa` по AGENTS.md; вне Herdr — сам проверяющий через playwright-cli. Тесты и браузер строго последовательно. В отчёте указать, кто выполнял проход, какие роли и сценарии проверены, точные команды и актуальное состояние кода. Если браузера нет, явно `render not browser-verified`; не объявлять C7 выполненным.
