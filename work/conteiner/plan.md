# Реестр и освидетельствования контейнеров

Состояние: active
Дата согласования: 2026-09-11
Уточнение: 2026-09-12 — сами контейнеры создаются вручную с нуля; ранее контейнерного раздела в текущей РВК не было.

## Цель и границы

Перенести бизнес-функционал старой системы в Jmix-приложение РВК: две самостоятельные страницы «Реестр контейнеров» и «Освидетельствования контейнеров». Карточка контейнера содержит девять вкладок: Описание, Характеристики, Операции, Накладные, Ремонты, Освидетельствования, Акты, Файлы, История.

«Реестр контейнеров» — самостоятельный справочник конкретных контейнеров с номерами. Создать новую таблицу `main.cnt_container` и форму «Создать контейнер», доступную редактору данных. Пользователь вручную создаёт контейнер и затем выбирает его при вводе ремонта, освидетельствования и других связанных записей. Контейнеры не появляются из внешнего источника и не создаются автоматически при вводе ремонта. Отдельный справочник типов/моделей описывает классификацию контейнера и не заменяет реестр самих контейнеров.

Все данные вводятся вручную, включая операции, накладные, ремонты и акты. Это уточнение пользователя заменяет первоначальное предположение о просмотре внешних данных. Новые справочники также редактируются вручную; организации и станции выбираются из существующего НСИ РВК. Дополнительные организации не создаются.

Не входят: миграция накопленных данных/файлов/истории, подключение ЭТРАН и старых MDM-источников, импорт Excel, конструктор полей/связей/валидаций, специальная массовая загрузка файлов, автоматические бизнес-расчёты, восстановление исторических версий. Функциональность реализуется стандартными средствами текущего UI, без копирования внешнего вида старой системы пиксель в пиксель.

## Общие решения

- Новый feature-domain `container` в `app`, таблицы `main.cnt_*`. Все общие контракты модели описаны в [contracts.md](contracts.md); `migration/ws_store` не изменять.
- Общие справочники вагонного и контейнерного разделов переиспользовать по назначению: подтверждены организации, станции и дороги (`VOrgPassport`, `VStation`, `VRailway`). Перед созданием остальных справочников проверить совпадение назначения, полей и ключей с существующим НСИ; одного сходства названий недостаточно. Не создавать контейнерные копии общих НСИ.
- Текущие сущности: генерируемый `Long id`, optimistic locking, аудит создания/изменения и soft delete. Старые системные `recdatebegin`, `recdateend`, `lastrec`, `trans_id`, `data_id` не переносить. Бизнес-даты договоров, ремонтов и освидетельствований сохраняются.
- Номер контейнера обязателен, нормализуется обрезкой крайних пробелов и переводом в верхний регистр; уникален также среди удалённых записей. Формат и контрольную цифру не проверять. Связи по внутренним id, а не номеру.
- Отдельная таблица полных снимков новых редактируемых сущностей. Аудит создания, изменения и soft delete атомарен с основной транзакцией. История и прежние файлы доступны только на чтение.
- Запретить удаление контейнера с действующими связями и удаление используемых справочников. Каскадного удаления нет. Общие документы не удаляются при снятии одной связи.
- Все три даты освидетельствования — без времени. Следующая дата в реестре вводится независимо. Стоимость, НДС, нагрузка, гарантии и модернизация крыши не рассчитываются автоматически.
- Роли: просмотр/экспорт; ввод данных, договоров и гарантий; ведение новых НСИ. Права действуют также на диалоги, историю, ссылки и вложения.
- Поиск, фильтры, сортировка, пагинация, настройка колонок, Excel-экспорт с русскими заголовками; без `genericFilter`. CRUD, просмотр и копирование — через общие формы; никаких действий закрытия периода записи.
- Каждый UI-таск поставляет свои messages, политики, проверки и рабочую интеграцию с каркасом карточки. T08 не заменяет проверки предыдущих тасков.

## Критерии всей работы

- Две страницы доступны из меню; девять вкладок работают на реальных сохранённых данных, без заглушек.
- При изначально пустой `cnt_container` редактор вручную создаёт первый контейнер из реестра, после чего выбирает его в ремонте и освидетельствовании. Для этого не нужны импорт, внешнее поступление контейнеров или ручной SQL.
- Все бизнес-поля матрицы доступны; количество и подписи колонок не ограничиваются видимой частью скриншотов.
- Освидетельствование из отдельного списка и карточки — одна запись, одна форма и единая история.
- Ручное создание данных, общие акты/накладные, файлы, поиск и экспорт работают без старой системы и миграции её записей.
- История полная и атомарная; отмена/ошибка не добавляет версию; конфликт изменений не перезаписывает данные молча.
- Все три роли проверены через UI и программный доступ; soft delete, запреты удаления и уникальность соблюдаются вне view-контроллеров.
- Выполнены статические проверки, обязательный `:app:test` и браузерные сценарии. Непройденный обязательный гейт не объявляется baseline-исключением.

## Проверка и передача

Для каждого таска прочитать применимые Jmix-skills до реализации. Незнакомые API проверять по подключённой документации или рабочему коду. Gate 1: IDE-инспекция каждого нового/изменённого Java/XML/properties/changelog; запасной путь — `./gradlew :app:compileJava` и механические проверки из `jmix-ide-static-analysis`. Проверки записать по файлам.

Gate 2: `./gradlew :app:test`. До него проверить `docker info`, compose, доступность PostgreSQL и `app/src/test/resources/application-test-local.properties`. При необходимости поднять инфраструктуру согласно AGENTS.md. Если wrapper не скачивается из корпоративного контура, сначала применить предписанный проектом публичный wrapper. Интеграционные тесты наследовать от `BaseIT`, UI-тесты — от `BaseUiTest`; данные удалять после теста, новые конфигурации Spring в наследниках не создавать. Точные команды выбранных новых тестов исполнитель указывает в `result.md`; один `--tests` не заменяет общий Gate 2.

Gate 3 для UI-тасков: последовательно пройти созданные экраны и действия через браузер. В Herdr делегировать `qa` по AGENTS.md; вне Herdr выполнить самостоятельно через `playwright-cli` и указать это. Приложение брать готовое либо поднять в фоне для проверки, дождаться `/actuator/health` = UP и остановить только свой процесс. `bootRun` не является гейтом. Без браузера указать `render not browser-verified`; задача не считается доказанно проверенной в UI.

Исполнитель передаёт результат в `ready_for_verify` с номером итерации. Только независимый проверяющий ставит `done`. После успешной проверки T08 закрыть работу через `task-close`; `summary.md` до фактического завершения не создавать.
