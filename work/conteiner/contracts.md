Предыдущее обсуждение варианта «редактируются только характеристики, освидетельствования и файлы» заменено последующим явным ответом «Ко всем данным». Операции/накладные/ремонты/акты должны иметь ручные формы, а не заглушки или внешние read-only views.

Реестр самих контейнеров наполняет редактор основных данных, даже несмотря на термин «справочник контейнеров». Роль ведения НСИ по-прежнему относится к видам/моделям/классификаторам. Порядок работы: вручную создать контейнер в реестре → сохранить → выбрать его в форме ремонта/освидетельствования либо открыть нужную вкладку карточки → вручную ввести данные и связи. Ввод номера в ремонт не создаёт контейнер неявно.

Схема контейнера уже найдена в разделе 2 [issue.md](input/issue.md): `CREATE TABLE ... "MDM_DATA".cont`. Дополнительный DDL от пользователя для создания основной таблицы контейнеров не требуется. Это старая схема для адаптации, а не существующая таблица текущей РВК.

## Единые правила модели

Предлагаемые таблицы ниже используют префикс `cnt_`, пакет `ru.fgk.ws.app.container`. T01 фиксирует фактические Java/entity/column names в этой матрице после сверки проекта; бизнес-состав и правила не меняются. Для JPA-связей — внутренние id и индексы, без физических FK согласно AGENTS.md. Имена/типы существующих НСИ не менять.

У всех новых обычных сущностей — `Long` + IDENTITY, optimistic locking, автор/время создания и изменения, soft delete. История не наследует mutable CRUD и сама себя не журналирует. `data_id`, `trans_id`, `lastrec`, `recdatebegin`, `recdateend`, `recdatenew`, `user_name` старой системы заменены новыми техническими полями; не являются бизнес-полями форм. Идентификаторы `row_id`, `file_id`, `act_id`, `contract_id`, `prop_id`, `id_char` и аналогичные старые PK заменяются генерируемым id новой сущности, отдельная копия старого id без миграции не нужна. В справочниках сохраняются настоящие бизнес-коды `code`, модель и наименования.

Бизнес-поля, в старом DDL допускающие NULL, не превращать самовольно в обязательные. Исключения новой структуры: обязательный номер контейнера; обязательный родитель у собственных дочерних записей; обязательные обе ссылки таблицы связи. Строковые размеры брать из исходного DDL; у view-полей без определения типа задать подходящий тип и длину в T01 и отразить в матрице. Не вводить неописанные расчёты, ограничения дат, регуляторные проверки или автоматическое заполнение дат значением today. День/время операции и даты получения не путать с техническим аудитом.

Ссылочные подписи, характеристики выбранной модели и длина из выбранного размера показываются из справочника. Остальные бизнес-значения ручные. Изменение справочника влияет на текущие отображаемые данные, но не изменяет старые снимки.

Наименования груза, операции, состояния накладной, плательщика и источника, для которых описанная форма не задаёт lookup, остаются текстовыми полями. НРП — самостоятельное текстовое значение; «Гружёный» — булево. Дороги отображаются по выбранным станциям, не вводятся вторым противоречащим значением. Это представления ссылок, а не автоматический бизнес-расчёт.

Операции/накладные — новые локальные таблицы, а не копии `CREATE VIEW` с ЭТРАН. Не создавать FDW, polling, REST DataStore, импорт, фоновые загрузки или запросы к сотням миллионов старых строк. Собственная операция принадлежит одному контейнеру; накладная является общим документом со списком контейнеров.

## История, файлы и транзакции

Общая таблица `cnt_entity_history`: тип сущности, id, версия/порядок снимка, действие CREATE/UPDATE/DELETE, автор, время, полный сериализованный снимок и версия формата снимка. Включать бизнес-поля, soft-delete-состояние, id и зафиксированные подписи ссылок, ссылки/имена файлов. Для общих актов/накладных снимок включает весь набор связанных контейнеров. В истории контейнера показывать версии самого контейнера; история дочерней записи/документа доступна в его форме, не подмешивается в версии родителя.

Изменение состава контейнеров общего документа должно менять его версию и снимок даже без изменения скалярных полей. Сохранение связей и снимка атомарно; выбирать момент снятия снимка после подготовки полного состава связей, без частично сохранённого промежуточного состояния. У операции DELETE сохраняется последнее бизнес-состояние с отметкой удаления. Отмена, no-op без изменений и rollback не создают ложную бизнес-версию. Повторно открытая форма ничего не сохраняет сама.

Журналировать все новые изменяемые доменные записи и справочники. Снимки защищены от изменения/удаления пользователями. Запись истории выполняется в транзакции persistence, без зависимости от открытого view и без фонового потока. Выбранный механизм Jmix проверить на реальных create/update/delete и rollback, а не только на загрузке Spring. Ссылки во время soft delete нельзя перечитывать обычной загрузкой уже скрытой записи; использовать проверенный способ получения последних значений.

Файлы: существующий `FileRef` и хранилище РВК; просмотр поддерживаемых типов через существующее средство, скачивание для остальных. Не переносить MDM `data_file`/`bytea`/`s3_uuid`. Заменённые и soft-deleted вложения физически не удалять, пока они доступны из истории. Исторические ссылки не должны открывать произвольный файл без проверки доступа к соответствующей записи. Отменённая загрузка не создаёт доменную запись/снимок; работу временных файлов согласовать с существующим хранилищем, не вводить новый фоновый уборщик.

## Общие документы, удаление и конкурентный доступ

Собственные характеристики, файлы, операции, ремонты и освидетельствования имеют обязательную ссылку на контейнер. Для общих актов и накладных в UI явно различать «Убрать из контейнера» и «Удалить документ». Первое меняет только связь и историю общего документа; второе — soft delete документа и отключение его действующих связей одной транзакцией. Другие контейнеры не удаляются. Предупреждение удаления общего документа перечисляет влияние на связанные карточки.

Наличие действующей собственной записи или связи с неудалённым актом/накладной блокирует удаление контейнера. Уже удалённые дети/документы и история сами по себе удаление не блокируют. Запреты справочников и договорных зависимостей учитывать по всем действующим ссылкам. Проверка ссылок и создание/удаление должны оставаться согласованными при конкурентных запросах; один UI-precheck недостаточен, физических FK нет.

Нормализация номера работает на любом пути сохранения; уникальность обеспечивается БД, включая soft-deleted записи. Изменение номера допустимо и не ломает ссылки; исторические подписи не переписываются. Для копии контейнера очищаются id, номер, аудит/версия/soft delete; переносятся поля описания и ссылки на НСИ, но не коллекции, файлы или история. Для копирования других записей также не переносить id/аудит/историю и вложения; в контексте вкладки сохранять её контейнер. У общего документа переносить поля шапки, а набор контейнеров пользователь задаёт явно; из карточки первоначально выбран текущий контейнер.

## UI и доступ

Меню содержит раздел «Контейнеры» с реестром, освидетельствованиями и группой новых НСИ. Договоры и гарантии доступны через формы выбора/редактирования связей; прочие старые самостоятельные списки автоматически не добавлять в меню. Общие формы используются и при открытии из списка, и из вкладки; возвращение после save обновляет только соответствующие данные.

Для нового контейнера сначала сохраняется описание. Редактирование дочерних данных доступно после получения id; не сохранять «сирот» ради предварительного открытия вкладки. Связанные коллекции загружать по id контейнера, с серверной пагинацией и при открытии вкладки, без полного чтения всех дочерних данных в fetch plan карточки. Неподключённые вкладки в промежуточных тасках скрыть; к T08 должны быть все девять рабочих вкладок.

Поиск выполняется по бизнес-полям текущего списка и отображаемым названиям ссылок, без содержимого бинарных файлов, старых версий и скрытых технических полей. Для дат/чисел предоставляются типизированные фильтры; текстовый поиск не заменяет их. Экспорт учитывает фильтры, сортировку, выбор колонок и права; применить существующую семантику выбора строк/всего результата РВК и отразить проверенные режимы в результате UI-таска. Не писать собственный Excel-движок или отдельную систему настроек.

| Роль | Права |
|---|---|
| Просмотр | Читать основные записи и необходимые lookup, историю и вложения; поиск, фильтры, экспорт; без create/update/delete |
| Ввод данных | Права просмотра + CRUD/копирование контейнеров, дочерних записей, общих документов, договоров/гарантий; НСИ только читать |
| Ведение НСИ | Читать необходимые данные для выбора и вести новые справочники; не даёт автоматически права изменять основные записи или существующий НСИ |

Роли могут назначаться совместно; определения ролей и view-id зафиксировать в T02. Для всех создаваемых сущностей предоставить MODIFY на редактируемые атрибуты; формы просмотра read-only. История пользователям доступна только на чтение. Не назначать новые роли существующим пользователям автоматически.
