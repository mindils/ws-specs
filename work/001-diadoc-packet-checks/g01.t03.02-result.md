## Сделано

- **Шаг `LegacyBusinessCheckStep`** (`BUSINESS`, `copiesToLegacyTable() = false`) стоит в составе
  всех типов `dispatch` между `ParseOutcomeCheckStep` и `DiadocViolationsCheckStep`. Порядок
  позиций в строке: `PROCESSING`, `BUSINESS`, `DIADOC`.
- **Чтение отметки.** `DiadocPacketCheckResultService.findLegacyMark(packet, type)` отдаёт
  `LegacyCheckMark`: итоговый код, тексты по колонкам (у каждой колонки свой уровень) и признак
  `WARNING_ECP`. Загрузка строк вынесена в общие `load*`-методы, их же теперь вызывает
  `findCheckResult`: новых запросов нет. Отметка читается по типу, по которому шла наработка, а не
  по типу пакета в зеркале: парсер пишет в таблицу этого типа.
  - контракты ТР-2 / ДЕП / КАП: `pack_checked_text` — с кодом пакета, `pack_warning_text` —
    WARNING, `listRelation.checkedText` — с кодом связи; итог `WARNING_ECP` — отдельная позиция
    WARNING «Пакет вагона-донора не подписан с двух сторон»;
  - Рем.Дет: `errors` — VIOLATION, `errors_warning` — WARNING;
  - ТР-1 и `dr_diadoc_oper_repair_packet`: одна колонка, уровень — общий код пакета.
- **Раскладка.** Код позиции `BUSINESS_<PacketDocumentType.name()>`, по позиции на строку текста
  (разделители `\r\n` и `\n`, пустые строки отбрасываются). Итог такой же, как у старой отметки,
  и `ok` наработки не меняется:
  - отметка «Норма» — ноль позиций, даже если в колонке остался текст;
  - отметки нет (нет строки или код пуст) — VIOLATION «Результат контроля не определён», как
    прежний `CHECK_FAILED` в `dispatchAndResolve`;
  - код не «Норма», но строк его уровня нет — добавляется общая позиция «Пакет не прошёл контроль»
    уровня кода;
  - отказ разбора — шаг отметку не читает: позицию уже дал `PROCESSING`, а отметка в таблице
    осталась от прошлой наработки.

## Решено без вас

- Модель отметки (`LegacyCheckMark`) и чтение по колонкам — в `DiadocPacketCheckResultService`,
  раскладка на позиции — в шаге.
- Связь МХ с кодом «Норма» позиций не даёт. Связь без кода получает уровень по коду пакета.
- Контракт с `pack_checked_code` = VIOLATION и неподписанным донором: старый итог
  `WARNING_ECP`, новая строка — VIOLATION (позиции нарушений + предупреждение ЭЦП). `ok` в обоих
  случаях `false`. Строка точнее старой сводки, которая из-за ЭЦП понижала нарушение.
- Тексты общих позиций («не определён», «не прошёл контроль») — те же, что раньше были в ответе
  `PacketParserService`, теперь через messages.
