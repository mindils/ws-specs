## Сделано

- **`AutoSignDecisionService`** (`diadoc.service`) решает, можно ли автоматически согласовать и
  подписать пакет. Возвращает `AutoSignDecision`: `blockers` (все найденные причины), `allowed()`,
  `items` (позиции строки с пересчитанными флагами Диадок; `null` без строки) и `documentIds`
  (свои документы для согласования).
  - `calculateAndStore(messageId, approvalType)` — для `/approve`. Записывает в строку позиции
    `DIADOC`, `status` и `auto_sign_*` через `PacketCheckService.saveAutoSignDecision`.
  - `calculate(messageId)` — для карточки (t05), без записи. Тип для настройки автосогласования
    берётся из строки, а без строки — из зеркала.
- **Пересчёт `DIADOC`:** из позиций строки убираются позиции `DIADOC` и прошлый `CHECK_FAILED`
  этого шага, добавляется свежий результат `DiadocViolationsCheckStep.check(packet, settings)`.
  Сбой шага даёт ту же позицию `PROCESSING`/`CHECK_FAILED`, что и при наработке. Для этого в
  `PacketCheckPipeline` появились public `runGuarded(step, packet, check)` и `isFailureOf(item, step)`.
- **Причины запрета** (коды — `AutoSignBlockerCode`, текст из messages `autoSign.*`, параметры —
  `entityId`, `messageId`, `status`, `packetType`):
  - `AUTOMATIC_APPROVAL_NOT_CONFIGURED` / `AUTOMATIC_APPROVAL_DISABLED` — карта
    `AUTO_APPROVAL_CODES` переехала в сервис, «1» = включено;
  - `PACKET_NOT_FOUND` — пакета нет в зеркале;
  - `CHECK_NOT_FOUND` — нет строки проверки;
  - `CHECK_VIOLATION` — одна причина, в тексте все нарушения через «; »;
  - `VIOLATIONS_NOT_CALCULATED`;
  - `PACKET_APPROVAL_UNAVAILABLE` — `checkCanApprove(messageId)` ≠ AVAILABLE;
  - `DOCUMENT_FINALIZED` — SIGNED/REJECTED/ANNULLED в зеркале;
  - `DOCUMENT_SIGNED` — наш `PacketDocumentFlow` SIGNED/SIGNED_REJECT по entityId, в любом
    сообщении;
  - `DOCUMENT_SIGNING_IN_PROGRESS` — незавершённый `PacketDocumentFlow` по entityId;
  - `RELATED_PACKET_APPROVAL_UNAVAILABLE` — `checkCanApprove(originalMessageId)` ≠ AVAILABLE у
    связанного документа;
  - `DOCUMENTS_NOT_FOUND` — нет своих документов.
- **Документы.** Ссылки грузятся без удалённых. Свои = не `relatedDocument` и не
  `supplementDocument`. Проверяются свои документы, а при `showRelatedDocuments` ещё и связанные.
  Дополнения не проверяются и не согласуются. Статусы `PacketDocumentFlow` по всем документам
  читаются одним запросом.
- **`PacketApprovalService.approve`:** `ok` из запроса не учитывается. Запрет — ответ
  `AUTO_SIGN_BLOCKED`: `message` — тексты причин через `\n`, `blockers` — список
  `{code, message, params}`. Разрешение — `approve` только по `documentIds`. В `ApprovePacketResult`
  добавлено поле `blockers`, в `ApprovePacketResponse` — `blockers` (без причин поле не выводится).
  Старые значения `ApprovePacketErrorType` остались в enum с пометкой «больше не выдаётся».
- **`DiadocPacketViolationCheckService` удалён.** `isSigningInProgress` и `describeDocument`
  вошли в сервис решения, `PENDING_DOCUMENT_FLOW_STATUSES` — тоже. Ключ
  `violation.relatedInSigning` удалён.
- **Без пользователя:** данные читаются через `UnconstrainedDataManager`. Есть исключение:
  `DiadocDocumentFlowService.checkCanApprove` и `NvProcessingSettingsService.getSettingValue`
  читают через обычный `DataManager`. Под `/approve` (system) это неважно. На карточке (t05)
  пользователю нужно право чтения `PacketFlow` и `NvProcessingSettings`.

## Решено без вас

- Тип для настройки автосогласования в `/approve` берётся из `packetType` запроса, как раньше.
  Неизвестный тип даёт «не настроено». На карточке тип берётся из строки, а без строки — из зеркала.
- При любом запрете `errorType` = `AUTO_SIGN_BLOCKED`. Коды причин, совпадающие с прежними типами
  ошибки, названы так же (`AUTOMATIC_APPROVAL_DISABLED` и др.). Прежние константы остались в enum.
- Нарушения строки дают одну причину `CHECK_VIOLATION` со всеми текстами, а не причину на
  позицию.
- Проверка «наш `PacketDocumentFlow`» смотрит строки по entityId во всех сообщениях. Поэтому
  незавершённые строки самого пакета могут продублировать `PACKET_APPROVAL_UNAVAILABLE` — так
  требует план («все найденные»).
- Без пакета в зеркале причины — `PACKET_NOT_FOUND` и при отсутствии строки `CHECK_NOT_FOUND`.
  Остальные проверки без пакета не выполняются.
- Сбой чтения настроек контрагента не превращается в причину: исключение уходит наружу,
  `/approve` отвечает `INTERNAL_ERROR` и ничего не согласует.
- Строки `USER_SKIP` для связанного документа и дополнения в `PacketDocumentFlow` создаёт
  существующий `acceptDocument`, по составу пакета из rvk-diadoc. Его по таску не трогал. В
  подписание (`NEW`/`SKIP`/`SETTINGS_MISSING`) попадает только свой документ.
