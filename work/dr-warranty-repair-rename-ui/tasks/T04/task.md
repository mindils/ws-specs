## Результат и контекст

Экранов у гарантийных ремонтов нет вообще. Согласовано: **две отдельные
формы** — эта задача про зону ДЭПС (заголовок отцепки + вкладки «Документы»
и «Допретензионная работа»), зона ДЮ — в [T05](../T05/task.md).

Пользователь ДЭПС создаёт претензию по отцепке и ведёт её до передачи в
претензионную работу.

Результат: list view поверх `VWarrantyRepairClaim`, detail view над
`LegalWarrantyRepairDeps`, пункт меню, i18n, политики в роли ДЭПС.

## Реализация

Скилы: `jmix-create-list-view`, `jmix-create-detail-view`,
`jmix-create-fragment`, `jmix-add-i18n-keys`, `jmix-style-ui`.
Палитра фиксируется собственными CSS-классами активной темы проекта;
при использовании токенов сначала подтвердить их в этой теме.

Пакет: `ru.fgk.ws.app.legal.warrantyrepair.view.deps`, ресурсы —
`app/src/main/resources/ru/fgk/ws/app/legal/warrantyrepair/view/deps/`.

### List view

`legal_WarrantyRepairDepsListView` (`StandardListView<VWarrantyRepairClaim>`),
`@ViewController` + `@ViewDescriptor`, XML в ресурсах рядом.

Фильтры — по параметрам старой процедуры `pThp_PretTehSelect2`
(`specs/dr-warranty-repair/02-old-procedure.md`, раздел параметров):
период ремонта, период браковки, номер вагона, дорога, депо ремонта,
виновник, вид ремонта, «подлежит/не подлежит выставлению претензии»,
реестр передачи в ДЮ, ПСР, плюс вычисляемые суммы из view.

Добавить даты и степени просрочки четырёх этапов ДЭПС: `Srok_PassDoc`,
`Srok_FilG`, `Srok_DoPret`, `Srok_PassPP`. Фильтры — диапазон даты и степень
просрочки для каждого этапа; сортировка и фильтрация до пагинации в БД.
Показать отдельный признак отсутствующего/неактуального расчёта из T02,
не смешивать его с отсутствием срока у неприменимого этапа.

**Только `propertyFilter` и `jpqlFilter`; `genericFilter` не использовать.**
Рабочий пример с `jpqlFilter` и фрагментом фильтров —

Открытие претензии из грида — detail view ДЭПС; скил

### Detail view

`legal_WarrantyRepairDepsDetailView`
(`StandardDetailView<LegalWarrantyRepairDeps>`).

- Шапка отцепки (`LegalWarrantyRepair` через ссылку `repair`) — **read-only**:
  номер вагона, дата браковки, дорога, депо, технологическая неисправность,
  дата и вид последнего планового ремонта, депо планового ремонта.
- `tabSheet` с вкладками, каждая — отдельный фрагмент
  (`jmix-create-fragment`), иначе XML становится нечитаемым:
  - **«Документы»** — блоки «Подлежит выставлению претензии», «Выданный
    телеграмм», «Приёмка рекламационных документов», «ВУ-41», «Передача
    документов», «Перевыставление тарифа», «Расчёт требований»,
    «Простой», «Передислокация в ремонт / из ремонта», «Ломаный тариф»,
    итоговые суммы;
  - **«Допретензионная работа»** — «Возврат на доработку в ДЭПС», письмо
    (номер/дата/сумма), рассмотрение письма контрагентом, передача в
    претензионную работу, ПСР, реестр передачи в ДЮ.

Точная раскладка полей по вкладкам и блокам —
`specs/dr-warranty-repair/03-old-form.md`, раздел «Зона редактирования
пользователя ДЭПС», плюс скриншоты
`specs/dr-warranty-repair/Зона редактирования пользователя ДЭПС*.png`.
Имена колонок в `03-old-form.md` — старой системы; сопоставление с новыми
брать из `05-column-mapping.md` с учётом переименований [T01](../T01/task.md).

Вычисляемые суммы («Простой: сумма», «Итого перевыставление платежей»,
«ВСЕГО к возмещению») на форме — read-only, обычные вычисляемые свойства
Jmix от значений формы с объявленными зависимостями. В гриде те же величины
берутся из view; совпадение формул проверить. Бизнес-логику во view не помещать.

Четыре срока и их подсветка на detail — read-only результат предварительного
расчёта сервисом T08 по текущему состоянию формы. После изменения исходных
полей обновлять результат без сохранения; ошибки календаря показывать явно.
Сохранение запускает транзакционный пересчёт T08; после закрытия формы
перезагрузить список. Отмена формы не меняет сохранённые сроки.

### Подсветка

Общие CSS-классы для обеих зон: нет просрочки — обычное оформление,
1 — жёлтый, 2 — оранжевый, 3 — красный. Палитра фиксируется в исходниках
темы, без пользовательской настройки и встроенных RGB-строк во view.
Подсвечивать соответствующую ячейку срока, а не всю строку: у одной
претензии этапы могут иметь разные степени. Дополнить цвет текстом степени
просрочки через messages; проверить читаемость и вычисленный стиль в браузере.
Даты порогов не показывать пользователю как отдельные технические колонки.

Поля зоны ДЮ на форме ДЭПС не показывать — для них своя форма.

## Критерии приёмки

- C1: пункт меню зоны ДЭПС виден пользователю с ролью
  `legal-warranty-repair-deps` и не виден пользователю только с ролью ДЮ.
- C2: список открывается, грид наполняется, фильтры по номеру вагона,
  периоду браковки и вычисляемой сумме отрабатывают.
- C3: из списка открывается detail view; шапка отцепки заполнена и
  недоступна на редактирование.
- C4: обе вкладки открываются, поля редактируются, сохранение проходит,
  значения читаются обратно из БД.
- C5: ни одного сырого `msg://` на экране, нет error overlay и серверных
  исключений в консоли/логе.
- C6: четыре срока ДЭПС отображаются с верной подсветкой; диапазоны дат и
  степени фильтруются на полном списке больше одной страницы, count корректен.
- C7: изменение базы обновляет preview; сохранение и повторное открытие
  дают те же сроки, отмена не меняет БД. Отсутствие календаря видно как ошибка.
- C8: фактический CSS в браузере соответствует каждой степени; текст
  сохраняет смысл без цвета, соседние ячейки с другими сроками независимы.

## Проверка

Гейт 1: инспекция IDE (`get_file_problems`) по **каждому** созданному файлу —
для `*-view.xml` это единственный статический способ поймать нерезолвящийся
`msg://`, неверный property path и отсутствующий data container. Запасное —
`./gradlew :app:compileJava` + скил `jmix-ide-static-analysis`.

Гейт 2: `./gradlew :app:test`. Красный `:app:test` после добавления view —
почти всегда отравленный реестр view (`package` ≠ каталогу, дубль
`@ViewController(id=…)`, `@ViewDescriptor` не резолвится в XML, пустой
`*-view.xml` → `SAXParseException: Premature end of file`). Это невыполненная
задача, а не «было до нас».

Гейт 3 (рендеринг): render-проход браузером по каждому новому view, кнопке и
полю. Внутри Herdr — делегировать агенту `qa` (`herdr agent get qa`, порядок
в `CLAUDE.md`), не тащить DOM и логи в свой контекст. Вне Herdr — самому
через `playwright-cli`; браузера нет вовсе — пометить
`render not browser-verified`. `bootRun` гейтом не считается: для
render-прохода поднимать в фоне, дождаться `/actuator/health` = UP, погасить.

В `result.md` — по каждому файлу вердикт статической проверки и по каждому
view/кнопке/полю, как проверено.
