## Результат и контекст

Вторая из двух согласованных форм. Пользователь ДЮ получает претензию,
переданную из ДЭПС, ведёт претензионную и судебную работу, фиксирует
получение денег.

Редактируемая сущность — `LegalWarrantyRepairDu` (1:1 с претензией). Строка
`_du` создаётся вместе с претензией сервисом из [T06](../T06/task.md); до
готовности T06 при разработке создавать её вручную в БД.

Симметрично [T04](../T04/task.md) — общая структура, скилы, гейты и правила
там же, здесь только отличия.

## Реализация

Пакет: `ru.fgk.ws.app.legal.warrantyrepair.view.du`, ресурсы —
`app/src/main/resources/ru/fgk/ws/app/legal/warrantyrepair/view/du/`.

### List view

`legal_WarrantyRepairDuListView` — тот же источник `VWarrantyRepairClaim`,
свой набор колонок и фильтров: номер и дата претензии, сумма претензии,
дата отправки виновнику, результат рассмотрения, реестр передачи в ДЮ,
номер дела и результат суда, дата и сумма получения денег, вычисляемые
`underpaid_cost` / `rejected_cost` / `in_review_cost` / `claim_deadline_date`.

Только `propertyFilter` / `jpqlFilter`.

### Detail view

`legal_WarrantyRepairDuDetailView`
(`StandardDetailView<LegalWarrantyRepairDu>`).

- Шапка отцепки и ключевые поля ДЭПС (виновник, подлежит ли претензия,
  суммы к возмещению, ПСР, реестр) — **read-only**: ДЮ их видит, но не правит.
- `tabSheet`, каждая вкладка — фрагмент:
  - **«Претензия»** — «Возврат на доработку в ДЭПС из претензионной работы»,
    «Рассмотрение претензии филиалом по виновному предприятию», блок
    «Претензия» (`claim_number`, `claim_date`, `claim_cost`,
    `claim_send_date`), «Рассмотрение претензии виновным предприятием»
    (дата получения, результат, дата и номер ответа, признанная сумма),
    «Отклонение претензии» (дата передачи в судебную работу, причина),
    «Получение денежных средств» (дата, сумма, № платёжного поручения,
    основание, примечание);
  - **«Судебная работа»** — номер и дата искового заявления, номер дела,
    сумма в исковых требованиях, результат, сумма к удовлетворению, аудит
    корректировки.

Раскладка — `specs/dr-warranty-repair/03-old-form.md`, раздел «Зона
редактирования пользователя ДЮ», плюс скриншоты
`Зона редактирования пользователя ДЮ*.png`. Имена в спеке — старой системы;
сопоставление через `05-column-mapping.md` с учётом переименований
[T01](../T01/task.md) (`claim_amount` → `claim_cost`, `lawsuit_amount` →
`lawsuit_cost`, `lawsuit_accept_amount` → `lawsuit_accept_cost`,
`at_fault_accepted_amount` → `at_fault_accepted_cost`, `payment_amount` →
`payment_cost`).

Внимание к двум похожим парам — их легко перепутать, в черновике спеки они
уже были перепутаны:

- `deps.rework_return_date` / `_rk_number` — возврат из **допретензионной**
  работы (`DoPret_Vozvrat_*`), это зона ДЭПС;
- `du.rework_return_date` / `_rk_number` — возврат из **претензионной**
  работы (`Pret_Vozvrat_*`), это зона ДЮ;
- `du.claim_reject_reason` = `Gar_Prich` — причина отклонения претензии;
- `deps.reclamation_reject_reason` = `Prich_Otkl` — причина отклонения
  рекламационных документов (ДЭПС), на форме ДЮ её нет.

### Меню, i18n, роль

Пункт в узле `legal` файла `menu.xml`; ключи в `messages_ru.properties`;
`@ViewPolicy` на оба view и `@MenuPolicy` — в `LegalWarrantyRepairDuRole` и
в полной `LegalWarrantyRepairRole`.

## Критерии приёмки

- C1: пункт меню зоны ДЮ виден пользователю с ролью `legal-warranty-repair-du`
  и не виден пользователю только с ролью ДЭПС.
- C2: список открывается, фильтры по номеру претензии, результату и дате
  получения денег отрабатывают.
- C3: detail view открывается по претензии, у которой есть строка `_du`;
  шапка и блок ДЭПС недоступны на редактирование.
- C4: обе вкладки редактируются и сохраняются, значения читаются обратно из БД.
- C5: пользователь с ролью ДЭПС, открыв форму ДЮ (если попал по ссылке), не
  может сохранить изменения.
- C6: ни одного сырого `msg://`, нет error overlay и серверных исключений.
