## Результат и контекст

У одной отцепки может быть несколько претензий, различаемых `claim_index`
(в старой системе — `Index_Pret`). Уникальность обеспечена частичным
уникальным индексом `(repair_uid, claim_index) WHERE deleted_date IS NULL`,
но кто-то должен вычислять сам индекс.

Форме ДЮ ([T05](../T05/task.md)) нечего редактировать, пока нет строки
`LegalWarrantyRepairDu`. Ответ пользователя на вопрос 5 в
`06-open-questions.md`: «тут последовательно надо создать» — значит `_du`
создаётся вместе с претензией, а `_case_one` остаётся `0..1` и создаётся
только при отправке карточки (вне объёма этой работы).

Результат: сервис создания претензии и сквозной интеграционный тест по всей
цепочке отцепка → претензия → зона ДЮ → строка db-view.

## Реализация

Скилы `jmix-create-service`, `jmix-create-test`.

`ru.fgk.ws.app.legal.warrantyrepair.service.WarrantyClaimService`:

- только constructor injection (field `@Autowired` в новых сервисах не
  использовать), бизнес-логика в сервисе, не во view;
- `createClaim(LegalWarrantyRepair repair)`:
  `claim_index` = max по неудалённым претензиям этой отцепки + 1 (при
  отсутствии — 1); создаёт `LegalWarrantyRepairDeps` и парную
  `LegalWarrantyRepairDu` с `deps_id`; всё в одной `@Transactional`-границе;
- `dataManager.save(...)` с отброшенным результатом → `saveWithoutReload(...)`;
- сложные выборки — `JmixDataRepository` / custom repository; следить за
  fetch plan и N+1 (скил `jmix-configure-fetch-plan`).

Кнопка «Создать претензию» в list view ДЭПС ([T04](../T04/task.md)) вызывает
этот сервис, а не создаёт сущности сама.

Если создание вынесено в слушатель события жизненного цикла entity вместо
сервиса — скил `jmix-add-entity-event-listener`. Код, выполняющийся вне
пользовательского запроса, здесь не появляется; если появится, нужен
`@Authenticated` или `SystemAuthenticator` (скил `jmix-run-background-code`).

## Критерии приёмки

- C1: первая претензия по отцепке получает `claim_index = 1`, вторая — 2.
- C2: вместе с претензией создаётся строка `LegalWarrantyRepairDu` с
  корректным `deps_id`; `LegalWarrantyRepairCaseOne` **не** создаётся.
- C3: после мягкого удаления претензии (`deleted_date`) новая претензия по
  той же отцепке создаётся без нарушения частичного уникального индекса.
- C4: созданная претензия видна строкой в `dr_v_warranty_repair_claim`,
  вычисляемые суммы совпадают с ручным расчётом.
- C5 (сквозной сценарий): пользователь ДЭПС создаёт претензию и заполняет
  свои вкладки → пользователь ДЮ открывает её в своей форме, заполняет
  «Претензию» и «Судебную работу» → обе записи сохранены, грид обеих зон
  показывает актуальные значения.

## Проверка

```bash
./gradlew :app:compileJava
./gradlew :app:test
./gradlew :app:test --tests "ru.fgk.ws.app.legal.warrantyrepair.*"
```

Интеграционный тест — наследник `app/src/test/java/ru/fgk/ws/app/it/BaseIT`
(профиль `test`, `@ExtendWith(AuthenticatedAsAdmin.class)`). Транзакцией
тесты не оборачиваются — проверяется реально записанное в БД, созданные
данные убрать в `@AfterEach`. **Своих `@TestConfiguration` и подмен бинов не
объявлять**: Spring кеширует контексты по ключу конфигурации, каждый такой
класс поднимает ещё один контекст приложения.

Сценарий C5 — браузером: внутри Herdr делегировать агенту `qa` (переключение
между пользователями двух ролей, заполнение вкладок, проверка сохранения,
console/network errors); вне Herdr — `playwright-cli` самому; браузера нет —
пометить `render not browser-verified`.

Точные команды и итог сквозного сценария записать в `result.md`.
