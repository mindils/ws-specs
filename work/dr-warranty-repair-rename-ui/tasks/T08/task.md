## Результат и контекст

Рассчитывать все семь сроков и пороги подсветки на Java по полному календарю.
Сохранять результат в отдельной таблице `main.dr_warranty_repair_deadlines`,
одна строка на претензию (`deps_id`, уникальный индекс). T02 присоединяет

Общий контракт — [план](../../plan.md),
[отличия](../../input/calendar-behavior-differences.md).

## Реализация

### Алгоритм и интерфейсы

- Java-сервис с constructor injection; чистый расчёт принимает снимок
  исходных полей, календарь и нормы. Возвращает семь дат окончания и для
  каждой — даты порогов +1/+10/+30 рабочих дней. Сервис также поддерживает
  предварительный расчёт без сохранения для detail-форм.
- Отсчёт со следующей даты после исходной; N=0 возвращает исходную дату.
  Отсутствие базы означает неприменимый срок. Пропуски календаря, неизвестная
  норма/тип — явная ошибка с диапазоном/операцией, а не пустой успешный расчёт.
- Начальные нормы и типы из T07. Промежуточные прибавления 14 дней —
  календарные. Не переносить SQL-функцию механически: согласованные отличия
  календарного алгоритма заданы отдельным документом.
- Перед кодом сопоставить старые имена с актуальными полями после T01.
  Выписать условия всех этапов из полного
  [SQL](../../input/pThp_PretTehSelect2.sql), а не только комментариев.
  Сохранить порядок пяти веток `Srok_PassPP`, ограничения по аренде/договору,
  исключение ДКФ, `NULL`-семантику сравнений и приоритеты `coalesce`.
- Учесть эффективное `Send_PD = coalesce(r.Send_PD, r.DatPret)`.
  Судебный возврат `Pret_Vozvrat_Dt > Send_PD` переопределяет срок отдельным
  правилом: не наследует WHERE предыдущего UPDATE. Отсутствие `_du` допустимо.
- `Dat_Pass` берётся из даты комплекта новой модели. Автомат 45 дней и
  обогащение внешними данными не добавлять. Не включать восьмой индикатор
  `Srok_FilOColor` и отчётные агрегаты `@Col` в этот таск.

### Сохранение и актуальность

- Entity расчёта в домене `legal.warrantyrepair`: технический Long ID,
  ссылка `deps_id`, семь групп дат (срок, +1, +10, +30), идентификатор
  ревизии календаря/норм. Текущий цвет и текущую просрочку не хранить.
  Для неприменимого этапа вся группа NULL; успешная строка расчёта существует
  даже при семи неприменимых этапах. Отсутствующая строка — расчёта ещё нет.
- Пересчитывать в транзакции изменения исходных данных: сохранение ДЭПС,
  ДЮ и общих данных отцепки. Изменение отцепки пересчитывает все связанные
  претензии. Не ограничиваться событиями нажатия кнопок UI.
  Слушатели/сервис не должны рекурсивно реагировать на запись своих результатов.
- Ошибка пересчёта откатывает изменение, а не оставляет старый срок рядом
  с новыми исходными данными. Сериализовать конкурирующие изменения одной
  претензии и публикацию календаря, чтобы последняя запись не вернула старый расчёт.
- Нужен идемпотентный массовый пересчёт существующих претензий и повторный
  запуск после прямого импорта. NiFi сейчас не реализуется, но обязательный
  вызов пересчёта после SQL-импорта описать в контракте интеграции.
- Завершить публикацию ревизий из T07: сначала полный успешный пересчёт,
  затем переключение актуальной версии. При ошибке новая версия не публикуется;
  предыдущие согласованные данные сохраняются. Для внешнего источника
  фиксировать снимок/ревизию, не смешивать дни разных версий в одном расчёте.
  Проверка изменения внешнего календаря должна предшествовать выдаче сроков
  как актуальных; при обнаружении изменения выполнить публикацию либо явно
  сообщить об ожидании пересчёта. Не допускать незаметного устаревания.
- При массовом расчёте загрузка календаря и норм пакетная, без SQL на каждый
  день/ячейку. Для закрытых претензий также пересчитывать сроки: версионирование
  исторических нормативов не входит в эту работу, применяются активные нормы.

Скилы: `jmix-create-service`, `jmix-create-entity`,
`jmix-create-liquibase-changelog`, `jmix-add-entity-event-listener`,
`jmix-configure-fetch-plan`, `jmix-create-test`. Если выполнение вне запроса —
`jmix-run-background-code` и реальная проверка вызова с аутентификацией.
Права на техническую запись расчёта даются внутреннему пути сервиса после
проверки прав на исходное изменение; конечный пользователь расчёт не редактирует.

## Критерии приёмки

- C1: все семь норм, ветки назначения, возвраты и NULL-сценарии покрыты
  тестами по первоисточнику. Предварительный и сохранённый расчёты совпадают.
- C2: примеры документа отличий дают новые ожидаемые даты; обычная неделя
  совпадает со старой функцией. Проверены переход года, рабочая суббота,
  последовательные праздники и недостаточный диапазон календаря.
- C3: после изменения базы, результата этапа или отцепки сохранённые сроки
  актуальны; при неприменимости старые даты очищены. Ошибка откатывает запись.
- C4: массовый пересчёт повторяем, публикация ревизии не оставляет смесь
  старых/новых расчётов; прямой импорт имеет явный путь восстановления расчётов.
- C5: техническая таблица не даёт пользователю права обходить ограничения
  ДЭПС/ДЮ; календарь не читается запросом на каждый день расчёта.
- C6: документ отличий дополнен ссылками на код/тесты и инструкцией
  пересчёта; результаты старой MSSQL не объявлены проверенными без запуска.

## Проверка

публикацию ревизий. Без собственных TestConfiguration, с очисткой данных.
