# Гарантийные ремонты: переименование колонок/таблиц и экраны ДЭПС/ДЮ

Состояние: active

## Цель и границы

Перенос функционала «Гарантийные ремонты / претензии по технологическим
неисправностям» из ВагТК (MSSQL, `dbo.TrkRemPretens`) в Jmix 3.

**Текущее поведение.** Этап 1 (модель данных) реализован в ветке
`f/caseone-task`, коммит `a72fc2ba3 «сделал структуру»`; в `main` не влит.
Есть 4 entity + 7 enum + одна роль + changelog-и
`320…323-legal_warranty_repair*.xml` + 234 i18n-ключа. Экранов нет,
`@ViewPolicy`/`@MenuPolicy` в роли нет.

**Требуемый результат.**

1. Таблицы переименованы в `dr_warranty_repair*`, колонки — по правкам
   пользователя из `specs/dr-warranty-repair/09-update.md`.
2. Появились экраны: отдельные list + detail формы для зоны ДЭПС и зоны ДЮ,
   свои роли, свои пункты меню.
3. Вычисляемые поля (суммы, срок предъявления) считаются в db-view, чтобы по
   ним работали фильтры грида.

**В границы работы не входит:** перелив данных из ВагТК (NiFi), отправка
карточки в Case.one, вкладка «Копии документов», сроки `Srok_*` с подсветкой,
сервис автозаполнения `dr_warranty_repair` из ЕО/ВагТК и НСИ.

## Общие решения

| Решение | Основание |
|---|---|
| Все реализованные колонки сохраняются; из 09 применяются только переименования (зачёркнутое → новое) и переименование таблиц | Ответ пользователя |
| Раскладка полей — как реализовано: блок «Претензия» в `_du`; `reclamation_note` отдельно от `reclamation_reject_reason`; `du.claim_reject_reason` = `Gar_Prich`; `deps.reclamation_reject_reason` = `Prich_Otkl`; `claim_contractor_guid` в `deps` | Исправления из `08-status-and-next-steps.md`, сверенные по `Таблица_претензий_с_колонками.xlsx` |
| Имена таблиц: `legal_warranty_repair*` → `dr_warranty_repair*` | `09-update.md`, шапка |
| Код **не переносится**: пакет `ru.fgk.ws.app.legal.warrantyrepair`, классы `LegalWarrantyRepair*`, имена Jmix `legal_WarrantyRepair*` — без изменений | Ответ пользователя; в 09 прямо сказано «код в `legal`, таблицы `dr_*`» |
| Денежные колонки — единое правило `*_cost` во всех четырёх таблицах | Ответ пользователя |
| Таблица `case_one` — колонки **без** префикса `case_one_` (как реализовано) | Ответ пользователя |
| Changelog переписывается **на месте**: файлы переименовываются, `createTable` сразу создаёт новые имена. `renameTable`/`renameColumn` не добавляем | Ответ пользователя: changelog-и нигде, кроме локальной БД, не применялись |
| Две отдельные формы (ДЭПС и ДЮ), каждая со своей ролью, своим list view и своим пунктом меню | Ответ пользователя; ответ на вопрос 8 в `06-open-questions.md` |
| Вычисляемые поля — в PostgreSQL db-view, а не `@JmixProperty`: по ним нужны фильтры грида | Ответ на вопрос 6 в `06-open-questions.md` |
| `legal_caseone_ref` и `legal_caseone_settings` не трогаем | Общие справочники домена `legal`, к warranty не относятся |
| Индекс `(wagnum, defect_date)` делаем уникальным | Ответ на вопрос 2 в `06-open-questions.md`: «это дело уникально» |
| `_du` создаётся вместе с претензией; `_case_one` — только при отправке | Ответ на вопрос 5; форме ДЮ нечего редактировать без строки `_du` |

**Ветка.** Работать в `f/caseone-task` либо в новой ветке от неё. В `main`
структуры нет — начинать с `git checkout f/caseone-task`.

**Правила проекта, критичные для этой работы** (`CLAUDE.md`): FK в миграциях
не создаются (`@DdlGeneration(unmappedConstraints = ...)`); preConditions
обязательны в каждом changeSet; `genericFilter` не использовать; весь UI-текст
через `msg://`; иконки — только реальные константы `VaadinIcon`; в сервисах
только constructor injection; `@ViewPolicy` на каждый view в каждой роли,
которая может его открыть, включая detail-формы из диалога.

## Критерии всей работы

- В `app/src` не осталось имён таблиц/колонок `legal_warranty_repair*`; в БД
  созданы `dr_warranty_repair`, `_deps`, `_du`, `_case_one` (197 колонок суммарно)
  и view `dr_v_warranty_repair_claim`.
- Пользователь с ролью ДЭПС открывает свой список, создаёт претензию по
  отцепке, заполняет вкладки «Документы» и «Допретензионная работа»,
  сохраняет; поля зоны ДЮ ему недоступны на запись.
- Пользователь с ролью ДЮ открывает свой список, открывает ту же претензию,
  заполняет «Претензию» и «Судебную работу», сохраняет.
- Грид фильтруется по вычисляемым колонкам db-view.
- Гейты: инспекция IDE по каждому файлу (для `*-view.xml` — единственный
  способ поймать нерезолвящийся `msg://`), `./gradlew :app:test` зелёный,
  render-проход браузером по каждому новому view.
