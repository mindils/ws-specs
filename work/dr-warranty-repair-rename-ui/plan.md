# Гарантийные ремонты: переименование колонок/таблиц и экраны ДЭПС/ДЮ

Состояние: closed

## Цель и границы

Перенос функционала «Гарантийные ремонты / претензии по технологическим
неисправностям» из ВагТК (MSSQL, `dbo.TrkRemPretens`) в Jmix 3.

**Текущее поведение.** Этап 1 (модель данных) реализован в ветке
`f/caseone-task`, коммит `a72fc2ba3 «сделал структуру»`; в `main` не влит.
Есть 4 entity + 7 enum + одна роль + changelog-и
`320…323-legal_warranty_repair*.xml` + 234 i18n-ключа. Экранов нет,
`@ViewPolicy`/`@MenuPolicy` в роли нет.

**Требуемый результат.**

1. Таблицы переименованы в `dr_warranty_repair*`, колонки — по правкам
   пользователя из `specs/dr-warranty-repair/09-update.md`.
2. Появились экраны: отдельные list + detail формы для зоны ДЭПС и зоны ДЮ,
   свои роли, свои пункты меню.
3. Вычисляемые поля (суммы, срок предъявления) считаются в db-view, чтобы по
   ним работали фильтры грида.
4. Все семь сроков этапов и подсветка доступны в списках и формах. Даты
   сроков и порогов рассчитываются на Java по полному производственному
   календарю и сохраняются; db-view обеспечивает фильтрацию и актуальную просрочку.
5. Гейт 2 держится строго зелёным: устранена гонка при конкурентной
   синхронизации OIDC-пользователя, из-за которой падает
   `SsoOidcUserMapperConcurrencyIT` (таск T09, решение по [Q03](questions/Q03.md)).

**В границы работы не входит:** перелив данных из ВагТК (NiFi), отправка
карточки в Case.one, вкладка «Копии документов», сервис автозаполнения
`dr_warranty_repair` из ЕО/ВагТК и НСИ, автомат даты полного комплекта по
реализации деталей и правилу 45 дней. Для сроков используется дата из новой
модели. Дополнительный индикатор `Srok_FilOColor` и старые агрегатные отчёты
`@Col` не расширяют согласованный набор семи сроков.

**Ветка.** Рабочая ветка — `feature/caseone-table` (содержит структуру caseone
и слияние с актуальным `main`).

**Правила проекта, критичные для этой работы** (`CLAUDE.md`): FK в миграциях
не создаются (`@DdlGeneration(unmappedConstraints = ...)`); preConditions
обязательны в каждом changeSet; `genericFilter` не использовать; весь UI-текст
через `msg://`; иконки — только реальные константы `VaadinIcon`; в сервисах
только constructor injection; `@ViewPolicy` на каждый view в каждой роли,
которая может его открыть, включая detail-формы из диалога.

## Критерии всей работы

- В `app/src` не осталось имён таблиц/колонок `legal_warranty_repair*`; в БД
  созданы `dr_warranty_repair`, `_deps`, `_du`, `_case_one` (197 колонок суммарно)
  и view `dr_v_warranty_repair_claim`.
- Пользователь с ролью ДЭПС открывает свой список, создаёт претензию по
  отцепке, заполняет вкладки «Документы» и «Допретензионная работа»,
  сохраняет; поля зоны ДЮ ему недоступны на запись.
- Пользователь с ролью ДЮ открывает свой список, открывает ту же претензию,
  заполняет «Претензию» и «Судебную работу», сохраняет.
- Грид фильтруется и сортируется по суммам, всем семи срокам и просрочке
  до пагинации. Итоговое число строк соответствует фильтру.
- Изменение исходных данных пересчитывает сохранённые сроки; изменение
  календаря/норм требует массового пересчёта. Ошибочные и устаревшие расчёты
  не выдаются за актуальные; отсутствие исходной даты отличается от ошибки календаря.
- Просрочка обновляется при следующем чтении списка после смены дня без
  ночного обновления цветов в БД; завершённые этапы сравниваются с фактом.
- Есть календарь с проверенным наполнением, НСИ норм и отдельная таблица
  расчётов; документ отличий дополнен ссылками на реализацию и тесты.
- Гейты: инспекция IDE по каждому файлу (для `*-view.xml` — единственный
  способ поймать нерезолвящийся `msg://`), `./gradlew :app:test` зелёный
  (`0 failing`, включая `SsoOidcUserMapperConcurrencyIT` — закрывается T09),
  render-проход браузером по каждому новому view.

- [Q03](questions/Q03.md) — resolved: красный `SsoOidcUserMapperConcurrencyIT`
  не связан с T01 (воспроизведён на базовой линии), причина — неработающая

  же работе таском T09, постоянного исключения из гейта 2 нет.
- Проверка источника календаря выполнена в T07 (2026-09-12) и закрыта:
  БД rvk-ws поднята из `docker/docker-compose.yml` на `localhost:5432`
  (порт занимает `docker-rvk-db-1`, а не посторонний PostgreSQL, как было в
  сессии разбора). Календаря нет ни в `main`, ни в `ws_store`, ни в
  `migration/ws_store`, ни в коде; отсутствие в корпоративной `ws_store`
  подтверждено пользователем. Выбран путь собственной НСИ в `main` —
  подробности и точные SELECT-ы в [результате T07](tasks/T07/result.md),
  источник и покрытие наполнения — в
  [документе отличий](input/calendar-behavior-differences.md).
- В этой среде у `specs` нет собственного `.git`; `git -C specs rev-parse
  --show-toplevel` указывает на основной проект. Перед фиксацией документов
  проверить фактическую организацию репозитория; `git -C specs commit`
  сейчас не обеспечивает отдельный коммит спецификаций.
