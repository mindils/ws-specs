# Претензии по технологическим неисправностям — модель данных и реализация

Контекст для постановки задачи: перенос функционала «Гарантийные ремонты /
претензии по технологическим неисправностям» из старой системы ВагТК (MSSQL)
в новую систему (Jmix 3, раздел `legal`).

**Имена.** Раздел называется `legal_tech_claim*`. Прежнее рабочее имя
`dr_warranty_repair*` (пакет `warrantyrepair`, классы `LegalWarrantyRepair*`)
встречается в файлах этой папки как история черновика: таблиц и классов с
такими именами в коде нет. Сводка соответствия старых и новых имён — в таске
[T01](../work/legal-tech-claim-ui/tasks/T01/task.md) работы
`legal-tech-claim-ui`. Имена колонок при переименовании не менялись, поэтому
маппинг в [05-column-mapping.md](05-column-mapping.md) действует как есть.

## Кратко о задаче

Старая система хранит всё в **одной** таблице `TrkRemPretens` (строка = одна
претензия; у одной отцепки может быть несколько претензий — `Index_Pret`).
Форма редактирования разделена на зоны прав по ролям:

- **Зона ДЭПС** — заголовок (вагон, отцепка, неисправность, ремонт) + вкладки
  «Документы», «Допретензионная работа»;
- **Зона ДЮ** — вкладки «Претензия», «Судебная работа», получение денег.

Новая система — **четыре таблицы модели** плюс таблица расчёта сроков:

1. `legal_tech_claim` — одна запись на **отцепку**, заполняется
   автоматически (из ЕО/ВагТК и НСИ), **уникальный ключ `repair_uid`**;
2. `legal_tech_claim_deps` — записывается при **создании претензии**
   (данные пользователей **ДЭПС**); суррогатный `id` — PK, `repair_uid` не
   уникален (несколько претензий на одну отцепку), UNIQUE
   `(repair_uid + claim_index)`;
3. `legal_tech_claim_case_one` — данные по карточке Case.one и результат
   отправки (по кнопке «Отправить»); связь **1:1** с `deps` (FK `deps_id`);
4. `legal_tech_claim_du` — данные пользователей **ДЮ**; связь **1:1** с
   `deps` (FK `deps_id`);
5. `legal_tech_claim_deadlines` — рассчитанные семь сроков этапов и пороги
   просрочки, одна строка на претензию (`deps_id` уникален).

## Границы задачи (согласовано)

- В этой спеке фиксируется **только модель данных**: сущности, Liquibase,
  enum'ы, маппинг колонок. Экраны, роли, сервисы и сроки спроектированы в
  работах `specs/work/` (см. «Что реализовано»).
- Интеграция с Case.one — **отдельная** задача.
- Переливка данных из ВагТК в новые таблицы — будет настраиваться **отдельно,
  вручную** (ЕО = единое окно РЖД данных; пока источник — ВагТК). Маппинг
  старых полей на новые для переноса — в [05-column-mapping.md](05-column-mapping.md)
  (раздел «Перенос данных»). Любой такой импорт обязан завершаться вызовом
  `TechClaimDeadlineService#recalculateAll()`: загрузка мимо приложения не
  порождает событий Jmix и сроков не считает.
- Код сущностей: пакет `ru.fgk.ws.app.legal.techclaim`,
  имена таблиц — `legal_tech_claim*`.
- Разделение колонок по таблицам сделано **по скриншотам формы**; в
  docx-заготовке «Технологические_неисправности_по_вагонам.docx» разделения
  нет (только черновик структуры отцепки) — имена колонок отцепки сверялись
  с docx (см. [06-open-questions.md](06-open-questions.md)).
