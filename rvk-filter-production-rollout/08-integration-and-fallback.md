## F08.2. Два независимых режима

**2026-09-07: реализовано для четырёх уже подключённых страниц.** `RvkFilterModes` подключён
в InitEvent их контроллеров. Старые propertyFilter и RVK имеют независимые условия;
возвращается applied, а не draft, переключение делает одну загрузку. Отмена/ошибка возвращает
режим, строки и пагинацию. Серверная настройка `rvk.filter.legacy-views` (список viewId через
запятую) принудительно включает старое поведение при открытии и блокирует переключатель.
Для N002 старых полей нет: отключение возвращает исходный список. Раскрытие details само
по себе не меняет режим. Новые приложения/сложные страницы этой проверкой не покрыты.


На каждой переводимой странице: новый фильтр сверху; старые элементы в `<details>` с локализованной подписью «Старые фильтры» и `opened=false`. Для этого проекта details уже используется и соответствует желаемой гармошке. Старые actions, IDs, bindings и сохранённые generic configurations остаются на месте.

Рядом явно показывать переключатель «Новый / Старый» и текущий режим. **Раскрытие details не переключает режим.** В неактивной панели поля/кнопки недоступны для изменений; её callbacks дополнительно защищены серверной проверкой режима.

| Момент | Обязательное поведение |
|---|---|
| Открытие переведённой страницы | Новый режим по умолчанию; старый details закрыт. Если серверный feature flag выключен — старый режим с видимой панелью |
| Переключение на старый | Сохранить draft/applied нового; снять его вклад; восстановить старый state/configuration; сбросить страницу; загрузить один раз |
| Переключение на новый | Сохранить старый state/configuration; отключить старые contributions; применить последнее успешно applied нового, не неприменённый draft |
| Первое включение режима | Использовать его выбранный default; не копировать автоматически значения другого режима |
| Изменение родительского контекста | Сохранить обязательные base query/params и собрать их с активным режимом; не восстанавливать устаревший parent id |
| Выгрузка / refresh | Использовать applied только активного режима |

Поддержать app feature flag по viewId для аварийного возврата всей страницы к старому режиму без релиза frontend. Настройка является серверной; URL/клиент не могут отменить принудительно выбранный старый режим. Для новых N-страниц откат выключает новый фильтр и оставляет исходный список; пустую «старую» гармошку не создавать.

## F08.3. Интеграция старого кода

- [ ] До переноса описать вклад каждого legacy property/jpql/genericFilter, hidden filter, PreLoad, value-change, apply button, URL/settings restore и начальных дат.
- [ ] Разделить обязательные domain constraints и пользовательские условия. Старые handler могут вызываться программно при restore: блокировать не только isFromClient, но и неактивный режим и фазу пакетного восстановления.
- [ ] Suspend применяет F04 API; не заменяет loader.condition на null и не вызывает reset(), который загрузит промежуточные данные.
- [ ] Восстановление нескольких полей выполнять с подавлением autoApply/load; после окончания одна загрузка. Нет промежуточного запроса без обязательного ограничения даты/родителя.
- [ ] Settings/URL для старого genericFilter остаются отдельными; новое состояние хранится под новым component key. Старые URL-параметры в новом режиме не должны скрыто ограничивать запрос.
- [ ] Смена пресета, Reset или user preferences не включает оба режима одновременно. Нужен тест с противоречащими друг другу условиями старого и нового фильтров.

Универсальная часть (state, condition building, suspend/apply, изоляция component) — аддон. Обвязка существующих listener/query/params на конкретной странице — app; не переносить legacy app-код в аддон.

## Приёмка

Неактивный фильтр не меняет condition/parameters, не делает load и не вмешивается в экспорт. Первое открытие, несколько переключений, reopen, URL/settings restore, смена parent и ошибка provider дают ожидаемые ID/count; в интерфейсе виден реальный активный режим. В отчёте страницы приложить результаты обоих режимов и команду/настройку выключения её flag.
