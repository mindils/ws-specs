# F05. Личные и общие пресеты, права и жизненный цикл

[К плану](README.md) · Репозиторий: `rvk-filter`; назначение ролей — `rvk-ws` · Статус: **не начато**.
Пилотный объём обязателен до M001; хранение и конкуренция зависят от F06.

## F05.1. Матрица прав

| Действие | Обычный пользователь | manageGlobal | manageAllConfigs |
|---|---|---|---|
| Читать общие пресеты доступной страницы | Да | Да | Да |
| Создавать/изменять/удалять свои личные | Да | Да | Да |
| Читать/менять чужие личные | Нет | Нет | Да, через административный путь |
| Создавать/менять/удалять общие | Нет | Да | Да |
| Назначать общий default | Нет | Да | Да |
| Копировать общий себе | Да | Да | Да |
| Сменить владельца чужого пресета | Нет | Нет | Только явная административная операция с аудитом |

Сохранить коды `rvk-filter-user`, `rvk-filter-config-row-level`, `rvk-filter-admin`, право `rvkfilter.manageGlobal`. Добавить независимое specific permission **`rvkfilter.manageAllConfigs`** и роль обслуживания `rvk-filter-maintainer`; последняя включает нужный CRUD и оба specific permissions. Назначение manageGlobal не даёт доступа к чужим личным.

Обычная панель всегда показывает только общие/свои для её component key, даже если пользователь является maintainer. Доступ ко всем пресетам — через отдельный административный экран. Пресет не предоставляет доступ к view/entity/строкам приложения.

## F05.2. CRUD и default

- [ ] «Сохранить как новый» создаёт запись с новым UUID; «Сохранить изменения» передаёт ID и ожидаемую version выбранной редактируемой записи. Название можно изменить без создания дубликата.
- [ ] Владелец, component key и scope обычного UPDATE неизменяемы. Перенос scope выполняется копированием; смена владельца/ключа доступна только явному admin operation.
- [ ] «Удалить» требует подтверждения с названием и scope; успешное удаление снимает selected preset, сохраняя уже applied условия до нового Apply/Reset. Повторное открытие удалённый default не применяет.
- [ ] Общий default меняется отдельным сервисным действием, проверяющим manageGlobal; не вызывать setDefaultForMe для global.
- [ ] Личный default — один на `(component_id, username)`, общий — один на component_id. Приоритет открытия: личный → общий → исходный page default.
- [ ] Личный default на основе общего создаётся действием «Скопировать себе», затем назначением default личной копии. Изменение исходного общего не меняет копию.
- [ ] Текущий пользователь определяется сервером. Обычный CREATE игнорирует/отклоняет присланного владельца; пустой scope, неизвестный scope и подмена component key не превращаются молча в user scope.
- [ ] Имя trim, непустое, максимум длина колонки 255; уникальность в scope/component сохраняет текущую чувствительность к регистру. Нарушение unique/version/удалённый конкурентом preset даёт понятное сообщение и обновление списка, не error overlay.
- [ ] При каждом действии заново загрузить запись и проверить права/version; cached DTO не является основанием разрешить запись. Save/delete/default/copy проверяют соответствие текущему component key.

## F05.3. Защита вне панели

- [ ] Сервисные проверки оставить на каждом изменяющем методе; бизнес-логика живёт в сервисах с constructor injection и транзакциями.
- [ ] Row-level защита должна покрывать READ и CREATE/UPDATE/DELETE обычного DataManager. Нельзя рассчитывать на JPQL policy чтения для защиты записи.
- [ ] Для UPDATE проверять **сохранённого** владельца/component/scope, а не только изменённый объект. Попытка сначала переписать username чужой записи на свой логин должна отвергаться.
- [ ] Для CREATE сервер запрещает обычному пользователю username=null и чужой username. Для DELETE проверяет сохранённую запись.
- [ ] Specific permission обслуживания используется явно в защищённом административном сервисе. Если для проверки оригинала нужен unconstrained load, выполнять только минимальное чтение и не возвращать его результат вызывающему; не переводить весь preset service в системную аутентификацию.
- [ ] Обычная row-level роль продолжает ограничивать чтение общими/своими. Выборку всех записей делает только отдельный admin service после проверки manageAllConfigs через узкий unconstrained путь; там же повторяются проверки допустимых изменений и version. Так политика «только своё» не блокирует обслуживание и не расширяет обычную панель. Resource и row-level роли назначаются отдельно; композиция разрешена внутри одного вида ролей.
- [ ] Entity CREATE сопровождается MODIFY разрешённых редактируемых атрибутов, не VIEW. Контекст страницы сохраняет свои права независимо от права сохранять пресеты.

## F05.4. Версии и валидация состояния

- [ ] Один валидатор используется при save, apply, выборе/default, admin-редактировании и импорте SQL-подготовленного payload. Проверять формат, version, field IDs, операции, значение/тип, размер и структуру групп.
- [ ] `schema_version` БД и версия payload согласованы. Версия 1 без поля version принимается как legacy v1; колонка не должна противоречить явной версии. Поддерживаемая старая версия мигрируется в памяти; persist — только после явного сохранения.
- [ ] Новое сохранение после F03.4 пишет v2. Чтение v1 преобразует существующие query/activeFieldIds/values в эквивалентный AND; сохраняет false, 0, массивы и relative dates.
- [ ] Неизвестная будущая версия, удалённое поле или потерянный доступ помечают preset несовместимым. Открытие экрана остаётся возможным; несовместимый default не запускает молча более широкую выборку.
- [ ] Разрешить владельцу/maintainer открыть несовместимый preset, увидеть потерянные поля и подтвердить исправленную копию/обновление либо удалить. Payload не перезаписывать фоновым чтением.

## Проверки

Два обычных пользователя A/B, менеджер global, maintainer; применять реальные resource/row-level роли, не только FullAccess. Проверить панель, сервис и прямой DataManager: чужой id, owner spoofing, global CREATE, смена scope/component, UPDATE по частично заполненному объекту, удаление, снятие права после открытия, имя-дубликат и конкурентная version. Браузерный флаг canManageGlobal/canSave не является авторизацией.

При отрицательной операции не должно быть изменений в БД. Успешная операция должна сохраняться после нового запроса/контекста. [JPQL и predicate политики Jmix](https://docs.jmix.io/jmix/security/row-level-roles.html).
