## Что доведено

Ранее старые propertyFilter и RVK одновременно участвовали в запросе через AND. Гармошка
только скрывала старые поля. Реализован F08.2 для четырёх действующих страниц:

- `RvkFilterModes.bind(...)` вызывается в InitEvent до первой автоматической загрузки.
- По умолчанию работает RVK; старые поля disabled, их autoApply выключен, собственные узлы
  условий исключены из base condition. Базовый JPQL и параметры загрузчика сохраняются.
- Переключение приостанавливает RVK через suspend/resume и загружает данные один раз.
  Возврат восстанавливает applied, сохраняя отдельный draft; старые значения также сохраняются.
- Ошибка или отмена загрузки возвращает прежний режим, строки, позицию пагинации и checkbox.
- `rvk.filter.legacy-views` задаёт серверный список viewId для аварийного возврата. Он применяется
  при открытии view, блокирует переключатель и не отменяется клиентским/Java value-change.
  После изменения properties нужен перезапуск приложения. Это не live-toggle для уже открытой view.
- На N002 старой панели нет: отключение RVK возвращает исходный список.

Пример конфигурации: `rvk.filter.legacy-views=nsi_NvPartType.list,nsi_VDepo.list`.
Пустое/отсутствующее свойство оставляет RVK включённым на всех четырёх страницах.

Из XML причин отклонения удалены неподдерживаемые `headerPartName` / `valuePartName`
(их не обрабатывают loaders Jmix 3.0.1). Описания трёх действий и подписи переключателей
вынесены в messages. Обработка других страниц автоматически не подключается.

Прямой SELECT по локальной БД подтвердил 6 / 3 / 9 / 8 / 31 для соответствующих условий
M001/M003. На всех четырёх страницах нет сырых msg:// и ошибок RVK. В консоли остаётся
ошибка загрузки аватара `info.main.vgk` (внешний корпоративный адрес не разрешается), а также
предупреждения dev mode; это не отказ фильтра. В серверном логе нет ERROR/исключений от
браузерных действий. При старте есть предупреждение необязательного AuthServerConfiguration.

На M002 дополнительно проверены 1280, 768 и 360 px: панель помещается по ширине,
поля и Apply/Reset доступны; скриншоты просмотрены. Это не полная матрица F07:
dark/Aura, 200%, 50+ presets и все клавиатурные сценарии здесь не проверены.
MultiSelect отсутствует в XML этих четырёх страниц: его browser-fixture из предыдущего
этапа не выдаётся за свежую проверку на host.

Приложение запущено собственным bootRun с временным Gradle init script, добавляющим actuator
только к проверочному runtime. `/actuator/health` на 8089 возвращает OAuth redirect 302;
статус UP не подтверждён. Сигнал готовности — `Started AppApplication` в логе и реальные
открытия views, как допускает fallback jmix-verify-bootrun. Gate 2 подтверждён завершающимися
тестами, а не bootRun. Лог: `/tmp/rvk-filter-active-browser.log`.
После проверки собственный AppApplication остановлен; порты 8080/8089 свободны.
Браузерная сессия закрыта; её артефакты перенесены в `/tmp/rvk-active-browser-artifacts`.
Временная база `rvk_filter_review_0b254becb4` удалена после проверки отсутствия соединений;

## Что ещё не закрыто

- Фиксированная опубликованная версия starter/addon для CI и production; сейчас MavenLocal SNAPSHOT.
- Роли аддона в Keycloak и host-приёмка под обычным пользователем, менеджером и maintainer.
  FullAccess-проход не подтверждает эти права; роли через таблицу не назначались.
- Startup definitions четырёх страниц в registry: без них admin-диагностика показывает
  UNKNOWN_COMPONENT и не разрешает назначать admin-default. Registry аддона реализован,
  определения приложения ещё не подключены.
- Открытые требования F02/F03/F07 (расширенный XML/Studio, reference providers, typed JPQL/IN,
  AND/OR, полный locale и accessibility) сохраняются. Не все они нужны текущим четырём
  простым страницам, но статус всего аддона этим проходом не закрывается.
- Новые страницы и массовые волны исключены из текущего задания и находятся в backlog.

Ни весь rollout, ни production-готовность не объявляются завершёнными. Этот отчёт закрывает
проверку перечисленных сценариев действующих страниц и реализацию их переключения режимов.
